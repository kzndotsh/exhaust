# Audit: morluto/rea

Source: [github.com/morluto/rea](https://github.com/morluto/rea), cloned shallow for this audit. "Reverse engineer anything with agents, from app behavior down to native binaries." One MCP server bridging an agent to real reverse-engineering tools (Ghidra, IDA, Hopper, Cutter, Frida, pwndbg, pwntools, mitmproxy capture) across native binaries, JavaScript/Electron, .NET, Android, and more. The user has used this tool directly against some of their own actual targets (ispmanager, Webmin, Roundcube), so this audit carries more practical weight than most of the others. Read-only, read by five subagents. See also the prior thirteen audits in this series.

## Adopted

**[ADR 0018](../adr/0018-tool-bridges-expose-a-narrow-enumerated-surface.md): tool bridges expose a narrow, enumerated method surface, never a raw command passthrough.** This repo shows both the right shape and the wrong one wrapping the same class of tool: its Ghidra bridge is a closed, default-throw method switch with mutation gating enforced server-side; its Cutter bridge accepts an arbitrary command string from an authenticated caller with no allowlist at all. The contrast is the clearest evidence yet for how the Rig's tool bridges should be shaped.

**[ADR 0019](../adr/0019-needs-confirmation-is-a-verdict-with-declared-requirements.md): `needs-confirmation` is a sixth Verdict, carrying what would resolve it.** This project has a durable, first-class record for exactly the state our Verdict model was missing: found something real, not yet confirmed or rejected, with declared requirements for what evidence would close it one way or the other. Our Finding model otherwise forces premature resolution or leaves a Finding with no Verdict at all, which our append-only design doesn't really allow.

**Two sharpenings of [ADR 0014](../adr/0014-eval-uses-blind-held-out-ground-truth.md)'s eval design.** First, an Oracle check should read raw bytes or actually execute recovered output rather than trusting the very tool it's checking to also report whether the check passed; this repo's strongest verifiers (an independent PCAP header parser, running recovered JavaScript for real and comparing its actual output) do exactly this, and it's a stronger standard than inspecting a claim's shape. Second, an explicit rule this project enforces with its own test suite: never let textual overlap with an expected answer stand in for factual correctness. Both are concrete additions, not new decisions.

## Reinforced, not new

**A fourteenth tool with no code-enforced restriction on what gets analyzed or attached to.** Frida's attach and spawn take a raw PID or program path with no ownership check whatsoever, relying entirely on OS permissions, and the project's own disclaimer says so plainly: "local operation does not establish authorization." Consistent with every prior audit.

**A real but entirely manual independent-oracle practice.** This project's development process genuinely does pin an external tool by exact version and SHA-256, compare a full corpus, and retain failing controls, exactly the discipline ADR 0008 calls for. But it happens by hand, during development, recorded in markdown, not automated or enforced at runtime. Another instance of a team that clearly understands the value of independent verification still not having built it into the product itself.

**CI genuinely does run real tools against fixtures with scripted, non-LLM assertions, for many formats at once.** A substantial number of workflows exercise real installed tools (Hopper, Ghidra, Wakaru, tshark, sigrok, solc) against generated or pinned fixtures, with the strongest one actually executing recovered JavaScript and checking its real output. This is a genuinely strong example of tool-level CI verification. But none of it scores an agent's analysis against blind ground truth; the project's own eval harness for that exists, states its own limits honestly ("free-form factual correctness is not assessed"), and isn't run in CI at all. The tool-verification and agent-evaluation problems are solved to very different degrees in the same codebase, which is worth remembering: solving one does not imply the other is solved too.

## New idea, not yet a decision

**A top-level skill structured as a routing table from target type to first tool**, rather than a flat catalog of skill descriptions competing for attention. Given our spine will likely decompose into many named sub-classes (per the Cloudflare and Anthropic-Cybersecurity-Skills audits), this is a concrete, simple mechanism for the entry point: route by what the Target actually is before anything else happens. Worth carrying into the spine-locking discussion, not decided here.

## Rejected, and why

- **Full generic script execution inside a tool bridge** (an option this project deliberately avoided for its strongest bridges). Confirms ADR 0018 rather than adding anything new.
- **A private code-loading mechanism with its own integrity check** (one bridge loads a signed extension jar via a custom class loader). Flagged by its own auditor as "a code-loading surface you would not want without review." Noted as a caution, not adopted.

## What this settled for exhaust

- [ADR 0018](../adr/0018-tool-bridges-expose-a-narrow-enumerated-surface.md): tool bridges expose a narrow, enumerated surface.
- [ADR 0019](../adr/0019-needs-confirmation-is-a-verdict-with-declared-requirements.md): a `needs-confirmation` Verdict with declared resolution requirements.
- [ADR 0014](../adr/0014-eval-uses-blind-held-out-ground-truth.md) sharpened: Oracles should read raw, independent evidence rather than trusting the checked tool's own report; never let textual overlap stand in for correctness.
- Material for spine-locking, not decided here: route by target type as the entry point into the spine.
