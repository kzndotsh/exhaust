# Cross-check: the 2026-10-26 Playbook proposal against primary testing-taxonomy sources

Source under review: [`docs/artifacts/2026-10-26-playbook-proposal.md`](../artifacts/2026-10-26-playbook-proposal.md), specifically its 12-item required baseline (§3, line 35) and 7-item reserved/gated table (§4, lines 41-49). This is **not** an audit of an external repo — it is this draft checked against primary standards and taxonomy sources, as additional input for whenever the Playbook catalog eventually gets locked. The draft itself stays exactly as written; nothing here edits it, the ADRs, or `GLOSSARY.md`. Per the proposal's own framing (and the standing instruction it quotes in its header), the Playbook catalog remains explicitly unlocked — these are findings to weigh later, not a verdict that settles anything.

Primary sources actually fetched for this cross-check (live, not from training-data memory):

- OWASP WSTG table of contents, current stable (v4.2): <https://wstg.owasp.org/v4.2/>
- OWASP WSTG GitHub category folders (post-4.2, includes the newer WebAssembly category): <https://github.com/OWASP/wstg/tree/master/document>
- OWASP ASVS 5.0.x chapter index: <https://cheatsheetseries.owasp.org/IndexASVS.html>
- PortSwigger Web Security Academy, full topic list: <https://portswigger.net/web-security/all-topics>
- PortSwigger/Burp knowledge base vulnerability list (partial — see limitation noted below): <https://portswigger.net/kb/issues>
- Repo's own existing nuclei-templates audit (not re-fetched, cross-referenced as written): [`docs/research/2026-10-26-nuclei-templates-audit.md`](2026-10-26-nuclei-templates-audit.md)

**Limitation flagged up front:** Burp Suite's own scan-check categories could not be pulled as a structured list — `portswigger.net/burp/documentation/scanner/audit/issue-definitions` 404s, and `portswigger.net/kb/issues` only renders a short nav sample (XSS, SQLi, CSRF, XXE, directory traversal, SSRF) via fetch, not the full issue catalog. Findings below lean on WSTG, ASVS, and the Web Security Academy topic list, which did return full structured taxonomies; Burp's documented categories are not independently represented here beyond that six-item sample.

## What the primary sources actually say

**WSTG v4.2 top-level categories (4.1–4.12; GitHub's current `master` adds a 13th, WebAssembly Testing, not yet in the stable release):** Information Gathering, Configuration and Deployment Management Testing, Identity Management Testing, Authentication Testing, Authorization Testing, Session Management Testing, Input Validation Testing, Testing for Error Handling, Testing for Weak Cryptography, Business Logic Testing, Client-side Testing, API Testing.

**ASVS 5.0.x chapters (V1–V17):** Encoding and Sanitization, Validation and Business Logic, Web Frontend Security, API and Web Service, File Handling, Authentication, Session Management, Authorization, Self-contained Tokens, OAuth and OIDC, Cryptography, Secure Communication, Configuration, Data Protection, Secure Coding and Architecture, Security Logging and Error Handling, WebRTC.

**PortSwigger Web Security Academy, all 31 topics** (from <https://portswigger.net/web-security/all-topics>), grouped as the site itself groups them:
- Server-side: SQL injection, Authentication, Path traversal, Command injection, Business logic vulnerabilities, Information disclosure, Access control, File upload vulnerabilities, Race conditions, SSRF, XXE injection, NoSQL injection, API testing, Web cache deception
- Client-side: XSS, CSRF, CORS, Clickjacking, DOM-based vulnerabilities, WebSockets
- Advanced: Insecure deserialization, Web LLM attacks, GraphQL API vulnerabilities, Server-side template injection, Web cache poisoning, HTTP Host header attacks, HTTP request smuggling, OAuth authentication, JWT attacks, Prototype pollution, Essential skills

## Q1 — Does the required-12 baseline omit a universal, target-agnostic WSTG/ASVS/PortSwigger category?

Two gaps stand out, both present as full top-level categories in **every** primary source checked and neither mentioned anywhere in the proposal (not required, not reserved, not in the "domain companions, not reserved yet" paragraph at proposal line 51):

1. **Configuration and deployment management.** WSTG 4.2 is a dedicated top-level category (admin interfaces, HTTP methods, backup/old files, cloud storage misconfig, HSTS) and ASVS gives it its own chapter, V13 Configuration. This is target-agnostic in the same sense ADR 0011 (line 5) demands of the required set — it applies "with no target type to hide behind" — yet it appears in neither the required-12 (proposal line 35) nor the reserved-7 table (lines 41-49).
2. **Cryptography / transport weakness testing.** WSTG 4.9 ("Testing for Weak Cryptography") is a top-level category, and ASVS splits it into two chapters (V11 Cryptography, V12 Secure Communication). Nothing in the required-12 or reserved-7 covers TLS/cipher weaknesses, padding oracles, or weak-crypto-at-rest as a distinct concern — "known-CVE" and "information disclosure" don't substitute for a dedicated crypto-weakness check.

A softer, partial gap: **WSTG 4.3 Identity Management Testing** (account enumeration, registration flow abuse, weak password-reset questions) is distinct from WSTG 4.4 Authentication Testing in the source taxonomy, while the proposal's required list folds "auth/session" into one bucket (line 35) with no explicit mention of identity-management-specific checks. This may already be intended to live inside the "auth" vertical's scope — the proposal doesn't say either way — so it's noted as a softer finding, not a clear omission like the two above.

## Q2 — Are the 7 reserved gate signals consistent with how primary sources describe triggering that category?

Checked each gate in the table at proposal lines 41-49 against the matching Web Security Academy topic (and WSTG/ASVS where applicable):

| Vertical | Proposal's gate | Cross-check |
|---|---|---|
| GraphQL | Confirmed `/graphql`-equivalent endpoint responding to an introspection probe | **Consistent.** PortSwigger's GraphQL API vulnerabilities topic describes exactly this detection path — probing for universal endpoints and introspection as the standard discovery technique. |
| WebSocket | Confirmed WS upgrade handshake observed in traffic | **Consistent.** Matches PortSwigger's WebSockets topic, which frames detection around observing the `Upgrade: websocket` handshake in traffic. |
| AI/LLM agent abuse | Confirmed LLM-backed endpoint (observed structured prompt/response behavior) | **Consistent.** Matches PortSwigger's Web LLM attacks topic, whose own methodology is to probe for LLM integration via crafted-input/response behavior rather than a keyword or dependency guess — the same discipline ADR 0011 requires. |
| Rate-limiting / brute-force | Confirmed unauthenticated or low-friction repeatable action (login, OTP, coupon) | **Consistent, but narrower than the source.** PortSwigger's Authentication topic treats brute-force protection as applicable to any credential- or secret-guessing flow, which the proposal's examples (login, OTP, coupon) capture reasonably well. No conflict found. |
| Proxy/transport parsing discrepancies (smuggling, cache poisoning, part of WebSocket surface) | Confirmed intermediary (reverse proxy, CDN, cache) observed via a header/behavior differential | **Partially imprecise — bundles two different trigger conditions.** PortSwigger's HTTP request smuggling topic keys off a front-end/back-end parsing *discrepancy* between two chained servers (detected via timing or differential responses), which does imply an intermediary. But PortSwigger's separate Web cache poisoning / web cache deception topics key off a *caching layer being present* (cacheable responses, keyed inputs) — a related but distinct signal from "an intermediary observed via header/behavior differential." Folding smuggling and cache poisoning under one gate description risks under-specifying the cache-poisoning half when this vertical's real skill file gets written (proposal §4's own text defers the "how-to-check-it procedure," line 39, so this may simply not be filled in yet — flagging it so the eventual skill file doesn't inherit the blur).
| Denial of service / ReDoS | Confirmed algorithmically-expensive endpoint behavior observed during recon | **Weakest-grounded gate of the seven.** None of WSTG, ASVS, or the Web Security Academy topic list (31 topics, above) carries a dedicated DoS/ReDoS testing category at all — WSTG historically dropped DoS testing from its methodology specifically because safely gating it is hard, and ASVS has no DoS-specific chapter. The proposed signal ("algorithmically-expensive behavior observed") is also the softest of the seven — it's a judgment call about performance characteristics rather than a hard, binary trust-boundary observation like "a `/graphql` endpoint responds to introspection" or "a WS handshake occurred." Worth a harder look when this vertical's real gate gets written, precisely because none of the checked primary sources models it as confirmable the way they do the others. |
| Supply chain (dependency confusion, exposed keys, SCM misconfig) | Confirmed CI/build pipeline or package-registry surface reachable/observable | **Not independently verifiable against the three named primary sources** — none of WSTG, ASVS, or the Web Security Academy topic list treats supply-chain testing as a category (it's OWASP Dependency-Check / SLSA territory, outside scope here). The nuclei-templates audit's own taxonomy (`exposures`, `misconfiguration` top-level dirs) is adjacent but doesn't specifically validate a CI/registry-surface gate either. No inconsistency found, but also no primary-source confirmation either way. |

## Q3 — Any required-vs-gate classification that looks debatable against these sources?

**Deserialization is the clearest candidate for reclassification toward gated.** The proposal lists it in the always-on required-12 (line 35). But the Web Security Academy's own taxonomy places "Insecure deserialization" in its **Advanced** group, not alongside the universal Server-side items (SQLi, access control, business logic, etc.) — PortSwigger's own framing is that this applies specifically where a target deserializes attacker-reachable serialized data (Java, PHP, .NET formats), which is a confirmable recon signal (observing a serialized-object format on the wire: Java magic bytes, PHP `O:`/`a:` strings, .NET ViewState), not a universal property every target has the way injection or access-control surfaces are. This looks structurally identical to what already earns a `gate` elsewhere in the table (e.g., GraphQL's introspection-probe gate) rather than what earns `required: true`. Worth weighing against ADR 0011's own bar (line 5): "a vertical that has to justify its place on every single Workspace, with no target type to hide behind, had better be genuinely universal" — deserialization's universality is less clear-cut than the other 11 required items.

**SSRF is a softer version of the same question.** PortSwigger's Server-side group lists SSRF among the universal-leaning topics (not Advanced), which supports the proposal's `required: true` choice more than it undercuts it — but SSRF exploitability still depends on a target actually having a parameter that triggers a server-initiated outbound request, a confirmable signal in the same spirit as the gated verticals' triggers. Flagged as debatable but weaker than the deserialization finding, and the proposal's current placement (required) has real support from PortSwigger's own grouping.

## Q4 — Any first-class primary-source category the reserved-but-not-yet-included list doesn't even mention as a future candidate?

Proposal line 51 names a specific set of categories it explicitly declines to reserve yet (Cloudflare's "memory-safety/kernel, desktop/IPC, cloud/IaC, protocols/RPC, resource exhaustion, data lifecycle" companions) and gives a reason (go past exhaust's actual targets to date). That paragraph does not mention the following first-class categories from the sources checked here, which are closer to exhaust's actual web-app target history than the Cloudflare items it does name:

- **HTTP Host header attacks** — a distinct, first-class Web Security Academy Advanced topic (password-reset-link poisoning, host-header-driven routing/SSRF, cache poisoning via Host header). It's adjacent to but not identical to the proposed "proxy/transport parsing discrepancies" gated vertical (lines 43-44) — Host header attacks don't require an intermediary/proxy at all, so bundling it silently into that vertical (if that's the intent) would miss single-origin cases. Not mentioned anywhere in the proposal, reserved or declined.
- **OAuth and JWT handling** — ASVS gives these two full top-level chapters (V9 Self-contained Tokens, V10 OAuth and OIDC), and the Web Security Academy lists "OAuth authentication" and "JWT attacks" as two separate Advanced topics. The proposal's required-12 folds "auth/session" into one line (line 35) with no mention of OAuth/JWT as a present or future candidate, despite both primary sources treating token-format and OAuth-flow testing as structurally distinct from generic authentication/session testing.
- **Configuration and deployment management, and cryptography/TLS weakness** — already flagged under Q1 as baseline omissions; they're repeated here because they're also absent from the declined-for-now list, meaning there's currently no record anywhere in this document that they were even considered.

## What this adds, not settles

None of this locks anything — the Playbook catalog, per the proposal's own header and ADR 0016, stays unlocked until the audit campaign is declared done. What this cross-check contributes for that eventual decision:

- Two apparent baseline gaps against every primary source checked (configuration/deployment management testing, cryptography/TLS weakness testing) with no mention in the required-12, the reserved-7, or the declined-for-now list.
- One gate description (proxy/transport parsing discrepancies) that conflates two source-distinct trigger conditions (request smuggling's front-end/back-end discrepancy vs. cache poisoning's caching-layer-present signal) — worth separating when that vertical's real skill file gets written, since §4's procedure is explicitly deferred to then anyway (line 39).
- One gate (DoS/ReDoS) that rests on a softer, more judgment-based signal than the other six, and isn't modeled as a confirmable category by any of the three named primary sources at all.
- One required-vs-gated classification worth a second look against ADR 0011's own universality bar: deserialization looks more like a gated vertical (PortSwigger's own "Advanced," not universal, grouping) than a required one.
- Three named candidates (HTTP Host header attacks, OAuth/JWT handling, plus the two Q1 gaps) that are closer to exhaust's actual web-app target history than the Cloudflare companions the proposal explicitly declines — currently absent from the "not reserved yet, add later" record entirely, so there's no paper trail that they were weighed and deferred versus simply not considered.
