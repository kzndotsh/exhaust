# Audit: mukul975/Anthropic-Cybersecurity-Skills

Source: [github.com/mukul975/Anthropic-Cybersecurity-Skills](https://github.com/mukul975/Anthropic-Cybersecurity-Skills), cloned shallow for this audit. Despite the name, this is a community project, not an official Anthropic one: "818 structured cybersecurity skills for AI agents, mapped to 6 frameworks (MITRE ATT&CK, NIST CSF 2.0, MITRE ATLAS, D3FEND, NIST AI RMF, MITRE F3), the agentskills.io standard, 34 security domains." A pure content library, not a harness or architecture, chosen to see what a skill collection at real scale (818 skills, many contributors) converges on. Read-only, read by three subagents.

## The sharpest finding: a half-working example of our own just-made decision

This library's main catalog file (`index.json`) does exactly what [ADR 0016](../adr/0016-no-hand-maintained-vertical-catalog.md) calls for: a committed generator script derives it from the skill files, a CI check fails a pull request if it's out of sync, and a push-time job self-heals any drift automatically. That half works correctly.

But several of the library's other documents (a coverage report, technique-mapping files) claim in their own text to be auto-generated by a script that is listed in `.gitignore` and doesn't exist anywhere in the repository's history. Nothing checks them. They disagree with each other and with the README on basic counts (805 vs. 817 vs. 818 skills; 218 vs. 257 vs. 291 techniques; four different ATT&CK versions cited across different files). A document claiming to be generated earns unwarranted trust compared to one that honestly says it's hand-maintained, and this is exactly that trap. Folded into [ADR 0016](../adr/0016-no-hand-maintained-vertical-catalog.md) as an amendment: a generator has to be committed and checked, not merely asserted.

**The library's headline claim about itself is the clearest "claims outrun code" instance found in this entire research project.** The README states every `mitre_attack` ID was "validated using the official mitreattack-python library... zero revoked or deprecated IDs." There is no such validation script anywhere in the repository, in CI, or in history. None of the actual validators check framework-ID fields at all; they're not even required fields. And it shows: a sampled SQL-injection skill maps to a process-injection technique ID that doesn't describe SQL injection at all, and the framework tags across a sample of related web-pentest skills look templated rather than individually chosen. Treat this project's "6 frameworks, rigorously mapped" marketing claim with real skepticism; the actual mapping quality, where checked, was poor.

## New decision

**[ADR 0017](../adr/0017-skill-descriptions-carry-a-routing-contract.md): a skill's description carries an explicit routing contract.** The one convention in this library that held up at real scale (818 skills, many contributors) is an enforced four-part description: what the skill does, an explicit "use when" trigger, keywords, and a negative trigger naming the nearest skill it could be confused with. This is what actually prevents two skills from competing for the same request, since a description is the only thing an agent sees before deciding what to load. Worth locking in before writing exhaust's own skill files, given our spine will likely decompose into many named sub-classes per vertical (see below).

## Material for the still-open spine question, not decided here

This library's granularity gives concrete, useful input for when the spine itself gets locked, without deciding it here.

**It splits by attack technique, not by broad category, and several of our verticals would decompose into many of its skills.** Our "access control" vertical maps onto separate library skills for broken access control generally, IDOR specifically, BOLA, and BFLA. Our "auth/session" maps onto four or more separate JWT-specific skills plus three or more OAuth-specific ones. This reinforces, with real-world granularity data behind it, that each vertical's internal shape should itself be a named sub-class catalog rather than one broad task, the same direction Cloudflare's audit pointed toward.

**Concrete gaps named precisely, some on our side alone and some on both.** HTTP request smuggling and cache poisoning/deception have no home in any of our 11 verticals. GraphQL- and WebSocket-specific testing are absent from our spine entirely. Race conditions are treated as their own distinct class in this library, not folded into logic flaws the way our spine currently does. Two gaps exist on both sides at once: neither this library nor our spine has a dedicated file-upload-specific skill, and web-application-specific known-CVE coverage is thin in both (this library's CVE-named skills are Active-Directory-specific, not web).

**Domain breadth confirms the same shape as Cloudflare's audit: a narrow core is defensible.** Of this library's 34 domains, only a handful (Web Application Security, Penetration Testing, API Security, and parts of Identity & Access Management) are directly relevant to active web-app pentesting; the rest (cloud posture, SOC operations, digital forensics, fraud, AI security, hardware) answer different problems entirely. Consistent with the earlier finding that your actual hunting targets don't call for Cloudflare's full breadth either.

## What this settled for exhaust

- [ADR 0017](../adr/0017-skill-descriptions-carry-a-routing-contract.md): skill descriptions carry an explicit routing contract (what, use-when, keywords, negative trigger).
- [ADR 0016](../adr/0016-no-hand-maintained-vertical-catalog.md) amended: a generator has to be committed and CI-checked, not just asserted as existing.
- Material for spine-locking, not a decision: verticals likely need internal sub-class decomposition; concrete named gaps (request smuggling/cache poisoning, GraphQL/WebSocket, race conditions as their own class); file-upload and web-specific known-CVE are thin everywhere, not just in our own spine.
