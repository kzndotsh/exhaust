## The headline finding: this is a real, converging open standard, not three vendors reinventing the same thing

agentskills.io states outright that "the Agent Skills format" was "originally developed by Anthropic, released as an open standard, and has been adopted by a growing number of agent products." Confirmed independently: Microsoft's Agent Framework docs name it explicitly as "Anthropic's Agent Skills format, verbatim," link to agentskills.io as the spec, and name interoperability as a goal ("reuse the same skill across different Agent Skills-compatible products"), listing Claude Code, Cursor, Codex, and GitHub Copilot as compatible. Cursor's own docs independently confirm the same shape (directory + `SKILL.md`, same required-field names). Vercel's skills.sh tooling also targets the same format for distribution/installation. Four independently-confirmed implementations agreeing on one shape is a real signal, not coincidence.

**The shape**: a skill is a *directory*, not a bare file, containing a required `SKILL.md` (YAML frontmatter + Markdown body) plus optional `scripts/`, `references/`, `assets/` subdirectories. Required frontmatter: `name` (≤64 chars, lowercase letters/numbers/hyphens only, must match the parent directory name — confirmed by Anthropic, agentskills.io, Cursor, and Microsoft independently) and `description` (≤1024 chars, must state both *what* the skill does and *when* to use it). Optional, from the open standard agentskills.io formalizes and Microsoft adopted verbatim: `license`, `compatibility` (free-text environment requirements), `metadata` (free-form string map, recommend unique keys per client to avoid collisions), `allowed-tools` (experimental, space-separated pre-approved tool list).

**Progressive disclosure is explicit and three/four-tiered everywhere it's specified**: Level 1 (`name`+`description`, ~100 tokens, loaded for every installed skill always) → Level 2 (`SKILL.md` body, loaded only once a skill is triggered, recommended under 5,000 tokens / 500 lines) → Level 3 (bundled scripts/references/assets, loaded only on actual reference; a script's own source never enters context, only its run output). Microsoft's version adds an explicit "load_skill tool" as the Level 1→2 trigger mechanism. agentskills.io adds a concrete nesting rule: keep reference-file chains to one level deep from `SKILL.md` itself — avoid deep nesting.

## What this means against exhaust's own already-written ADRs: independent convergence, not a gap to close

Three of exhaust's own ADRs, written before this audit and without reference to the open standard, land on structurally identical reasoning:

- **ADR 0013** (skills use progressive disclosure): "a short top-level entry... and a separate, more detailed doc that only gets loaded... when that vertical or tool is actually invoked" is, almost word for word, the open standard's Level 1 → Level 2 split.
- **ADR 0017** (skill descriptions carry a routing contract): "a description is the only text an agent sees before deciding which skill to load; the body never gets read until that decision is already made" is the exact same claim the open standard's `description` field requirement is built on (state what *and* when, because that's all that's visible pre-trigger).
- **ADR 0022** (community skill content is signed and verified): goes further than every single source checked here. None of Anthropic, agentskills.io, Microsoft, Cursor, or Vercel specify any cryptographic signing or provenance mechanism for third-party skills — every one of them relies on "only install from trusted sources" plus a manual-audit recommendation (Anthropic's enterprise tier adds an opt-in content-scanning feature, still not a signature check). This is confirmed as a deliberate point where exhaust's own design is stricter than the field it's drawing from, not an oversight to fix.

No contradiction found anywhere between exhaust's existing design and the open standard's actual shape. The two differences worth naming as decisions, not accidents:

1. **`name` matching the directory name** is a convention exhaust's §2 schema doesn't currently state explicitly, though `skills/README.md` already implies the same one-subdirectory-per-vertical shape. Worth adding as an explicit, generator-enforced rule (fail the generator, not just note it in prose) — cheap, and every implementation checked enforces it.
2. **`description`/`use_when`/`do_not_use_for` as three separate fields** (ADR 0017) versus the open standard's single `description` field expected to carry both halves in prose. This is a deliberate, justified departure, not a gap: exhaust's routing contract is lint-checked as three distinct pieces specifically because near-neighbor verticals (IDOR/BOLA/BFLA) make ambiguous routing a real failure mode at the scale exhaust's catalog is heading toward — a stricter, more literally-checkable contract than "write a good description," which is all the open standard asks for. No reason to collapse these back into one free-text field; exhaust's own vertical skill files are read by exhaust's own bespoke generator, never by a literal Agent-Skills-compatible runtime, so there's no interop cost to staying stricter.

## `cursor/plugins` at real scale: a plugin manifest layer above `SKILL.md`, a real alternative to routing-by-description, and a genuine anti-pattern caught in the wild

Cursor's own plugin repo adds a layer above individual skills that none of the nine original sources had: `.cursor-plugin/plugin.json`, a strict JSON Schema (`additionalProperties: false`) covering the whole plugin — `name` (kebab-case, regex-enforced), `version` (semver), `author`, `license`, `keywords`, and glob-pattern pointers (`skills`, `agents`, `rules`, `commands`) into where each component type's files actually live. Individual skills underneath still use the same `SKILL.md`-with-frontmatter shape confirmed everywhere else in this audit — `pstack/skills/architect/SKILL.md` has exactly `name`, `description`, and one more field not seen before: `disable-model-invocation: true`.

**`disable-model-invocation` is a genuinely useful idea exhaust doesn't have yet.** It marks a skill as never autonomously selected by the orchestrator matching its description against a request — only reachable when another skill names it explicitly. `pstack` uses this at real scale: it ships 56 separate `principle-*` skills (one per named engineering principle — laziness, root-cause-fixing, foundational-thinking, and so on), every one of them `disable-model-invocation: true`, each invoked by name in prose from higher-level orchestrating skills ("Run the **how** skill," "the **exhaust-the-design-space** principle skill made concrete") rather than left to autonomous routing among 56 similarly-scoped descriptions. This is a direct, workable alternative (or complement) to ADR 0017's routing-contract-lint approach for exactly the near-neighbor problem ADR 0017 names as its own motivating example (IDOR vs. BOLA vs. BFLA): instead of (or alongside) making every vertical's description maximally distinguishing for autonomous model-driven selection, a fine-grained sub-vertical could be marked non-autonomous and explicitly dispatched by the Harness's own vertical-picking logic once recon narrows which one actually applies — turning a fuzzy selection problem into deterministic dispatch for the cases where that's possible. Worth weighing against §7.5's still-open "how deep sub-vertical decomposition goes" question.

**A real anti-pattern, caught by actually reading the files, not assumed:** `pstack`'s own top-level `poteto-mode/SKILL.md` embeds a hand-written "Principles" index — one line per principle skill, each a paraphrase of that skill's own `description` — directly in its body. Comparing them side by side: `principle-laziness-protocol/SKILL.md`'s actual description is *"Apply when refactoring, evaluating diff size, or tempted to add abstractions, layers, or signal threading. Bias toward deletion and the smallest change that solves the problem."* `poteto-mode/SKILL.md`'s own line for the same principle reads *"Refactoring, sizing a diff, or tempted to add abstractions, layers, or signal threading. Bias to deletion and the smallest change that solves the problem."* Close, but not identical — two independently-maintained descriptions of the same skill, with nothing to catch them drifting further apart over time. No generator, build script, or CI check found anywhere in the repo that derives one from the other. This is a live, present-day instance of exactly the failure mode ADR 0016 is designed to prevent, found in an actively-used, officially-distributed plugin, not a hypothetical. It doesn't change anything about exhaust's design — it's independent confirmation that the discipline is worth the extra rigor, from a concrete example rather than an abstract risk.

**Cursor's own quality gate for plugin submissions is also a checklist, not a generator.** `create-plugin/skills/review-plugin-submission/SKILL.md` — Cursor's official pre-publish review skill — is an agent-run or human-run checklist ("Verify manifest validity," "Verify component metadata," pass/fail report, prioritized fix list), not an automated build step with a CI gate. This reinforces the main finding below from Cursor's own first-party tooling, not just third-party skill authors: nobody checked in this audit, including the platform vendor's own official submission-review process, uses a generated-and-CI-diffed catalog as the actual enforcement mechanism.

## Correction: `cursor/plugins` *does* run a generated-and-CI-diffed artifact, just not a catalog

The tenth-source finding above states that "nobody checked in this audit, including the platform vendor's own official submission-review process, uses a generated-and-CI-diffed catalog as the actual enforcement mechanism." That conclusion is about Cursor's plugin-*submission* review specifically, and it still holds for that one piece. But a deeper read of the same repository (`scripts/generate-pstack-harness-trees.mjs`, confirmed as a real, present script, not just README prose) found exactly the mechanism ADR 0016 wants, applied to a different kind of artifact: it rewrites `pstack/` into a second, complete translated tree at `harness/pstack/claude-code` (Cursor-term detection, relative-link rewriting), and `.github/workflows/validate-plugins.yml` runs it with `--check` in CI, failing the build the moment the committed copy drifts from a fresh regeneration. The wrinkle worth naming: this generator's output is a *whole second plugin tree per target harness*, not a single JSON index the way exhaust's `catalog/verticals.generated.json` is — a heavier-weight instance of the same discipline, solving cross-harness translation rather than metadata extraction, but the generate-then-`--check`-in-CI shape is identical to what ADR 0016 already specifies.

This repository also ships two more pieces of real machinery worth recording, both found by reading the scripts rather than the docs:

- **`skills/poteto-mode/scripts/check-plan.mjs`** is a genuine structural linter for agent-authored planning documents, not a skill file: it parses a plan's Markdown and asserts exact section order, required sub-block sequences per entry, a numbered checklist's completeness, and even prose-style rules (no em dash, no curly quotes, no mid-sentence colon), exiting non-zero on any violation. It's evidence that ADR 0016/0017's generated-and-checked discipline generalizes past skill *catalogs* to other agent-produced artifact types (plans, reports) — worth remembering if exhaust ever needs to validate the shape of a Harness-produced report the same mechanical way, rather than trusting an agent's own formatting.
- **A two-tier skill taxonomy, cross-referenced by name rather than two separate directories.** Beyond the `disable-model-invocation` flag already documented above, `pstack` draws a real line between *routing/workflow skills* (playbooks, `how`, `why`, `architect`) and *non-invocable reference skills* (the 56 `principle-*` files), the second group existing purely to be cited by name from the first, never matched against a request's description on their own. This sharpens, rather than replaces, the existing `disable-model-invocation` finding: it's not just a flag on an otherwise-ordinary skill, it's a whole second class of skill file with a different job (a citable unit of doctrine, not a dispatchable procedure). Exhaust's own vertical files don't currently have an equivalent of "a principle cited by several verticals' procedures but never dispatched on its own" — worth a note next to the still-open `disable-model-invocation`-equivalent question already on this document's own list, below.
- **A per-role, not per-skill, model-override sheet with a documented fallback ladder.** `/setup-pstack` writes one generated rule file (`~/.cursor/rules/pstack-models.mdc`, `~/.claude/rules/pstack-models.md` in the Claude Code port) with one line per *role* (`feature, refactoring: ...`, `judgment and prose: ...`, plus named panel roles), a budget token mapped onto a shared reasoning-effort ladder, and explicit degrade-to-nearest-detected-model and reject-once-never-retry behavior written into the router skill itself. Not directly applicable to exhaust today (exhaust's `AgentSession` takes one model per run, not per-role dispatch across many concurrent delegates the way `pstack`'s subagent-heavy workflow does), but worth remembering if exhaust's Harness ever grows a multi-model delegation shape of its own: a generated, separately-versioned override file beats hardcoding a model choice inside any one vertical's procedure.

## `michael-denyer/pstack-claude`: the strongest real-world precedent for ADR 0016 found in this entire audit

This repository's job is harder than exhaust's own generator problem: it maintains a complete, edited-for-a-different-platform copy of someone else's plugin, forever, as that upstream keeps changing underneath it. Its solution is worth describing in full because it's a more rigorous version of exactly what ADR 0016 asks exhaust's own catalog generator to be.

**`CONTRIBUTING.md`'s "sync boundary" section draws the line explicitly and enforces it by machine, not by convention.** "Upstream owns skill content. This port owns the Cursor-to-Claude-Code translation." Every file that diverges from a mechanical translation of upstream must have an entry in `tools/forks.json` — its kind (`port-feature` for unavoidable platform mechanics, `policy` for a deliberate kept behavior), a one-sentence `why`, and the release it was introduced in. `bun tools/sync.mjs` fails the run and writes nothing if any forked, merged, or conflicted path lacks a declaration, *and* fails if a declared fork's path no longer exists or no longer actually differs from upstream — a bidirectional staleness check, catching both an undeclared divergence and a stale declaration nobody cleaned up, enforced at sync time rather than left to a human noticing.

**`tools/substitutions.json` is the literal, auditable mechanism behind every Cursor-to-Claude-Code terminology rewrite**, not a hand-applied convention: a JSON file of roughly 99 `{pattern, replacement, rationale}` rules (some scoped to specific files via a `files` key) plus a 27-entry denylist of tokens that should never appear unrewritten (`grok-`, flagged with a hint pointing at the fix), and `bun tools/sync.mjs --check-rules` — run in CI — fails the build if any rule matches zero files at the currently-pinned upstream commit, forcing a stale rule to be deleted rather than silently rot into dead weight nobody notices. Every rule carries its own rationale inline, so a reviewer can tell *why* a rewrite exists without archaeology.

**`tests/skill-rules.test.mjs` pins exact prose, not just schema**, and does it for a stated reason written directly in the test file's own header: "A rule dropped in either reads as a clean sync, so each one is pinned here by the sentence that carries it, with the issue or PR that earned it." Confirmed with a real entry: a test asserting that `create-verification-skill/SKILL.md` still contains the literal phrase `"YAML frontmatter (\`name: verify\`"` word for word. This is a mechanism exhaust doesn't have an equivalent of yet: a regression test that fails if a specific, hand-chosen sentence silently disappears from a generated or hand-maintained file during a future edit, catching prose drift a schema-only check (like `catalog.py`'s current `MalformedSkillFileError` checks) structurally cannot catch.

**`tools/generate.mjs`'s own file header states the exact CI contract ADR 0016 wants, almost verbatim**: "`bun tools/generate.mjs --check` writes nothing and fails when a committed copy is stale, so it cannot ship." `.github/workflows/ci.yml` runs exactly that in a dedicated `generated` job, plus `bun tools/sync.mjs --component --dry-run` and `--check-rules` as separate jobs. This is the single clearest real-world instance, across this entire twelve-source audit, of "regenerate, diff against what's committed, fail the build on drift" as the literal enforcement mechanism — a stronger, more directly applicable precedent for exhaust's own `exhaust catalog check` than `intellectronica/ruler` (§ below), because it's the exact same `--check`-flag-fails-on-staleness shape exhaust's own `catalog.py` already implements, independently arrived at for a structurally similar problem.

**`CHANGES.md` records a declined upstream change with a concrete, file-specific reason, not a silent skip**: "Upstream's `worktree-audit.sh` fix for GNU `stat` does not apply, because the port excludes that script and runs `worktree-audit.mjs`." Worth naming as the pattern for exhaust's own future ADR-addendum convention (already used for ADR 0021/0025/0026's own "Implemented"/"Resolved" follow-up paragraphs in this repo): when something from outside confirms or conflicts with a settled decision, record why it was or wasn't adopted, scoped to the specific mechanism, not left as an unexplained absence.

## `pbakaus/impeccable`: a third real-world generated-catalog precedent, with a looser staleness policy worth naming as a deliberate alternative

A thirteenth source, added at the user's request: `github.com/pbakaus/impeccable`, a design-system tool whose own agent-skill content is authored once (`skill/SKILL.src.md`) and generated out to over a dozen target harnesses (`.claude/`, `.cursor/`, `.gemini/`, `.codex/`, `.devin/`, `.kiro/`, and more, each with its own `skills/` subtree), audited by a delegated subagent against the exact same local-clone-not-fetch discipline used for the two prior deep repository audits in this document.

**The generator is real** (`scripts/build.js`, "Transforms source skills into provider-specific formats"), but its CI enforcement is a genuinely different, looser shape than every other precedent in this audit. `.github/workflows/sync-generated-output.yml` regenerates the tracked output and diffs it (`git status --porcelain -- $GENERATED_PATHS`), but on drift it auto-commits and pushes the regenerated output straight to `main`, with a retry/rebase loop for races — "regenerate and self-heal post-merge," not "fail the PR pre-merge" the way `michael-denyer/pstack-claude`'s `tools/generate.mjs --check` or `cursor/plugins`' own `--check`-flagged job both do. `AGENTS.md`'s own "Generated Provider Output Policy" states the tracked harness folders "stay tracked... They are still generated artifacts" — an explicit, named decision, not an oversight. Worth recording as a third real option alongside "fail CI on drift": self-healing auto-commit trades a failed PR for a silent corrective commit nobody reviewed before it landed on `main`. ADR 0016's own fail-closed discipline (CI fails, a human fixes it, nothing lands un-reviewed) is the stricter of the two, and this finding is the first time this audit found a real project that deliberately chose the looser alternative and named why.

**Per-harness adaptation is genuine, not a byte-identical copy** — confirmed by diffing `.claude/skills/impeccable/SKILL.md` against its `.gemini/` and `.cursor/` counterparts directly: frontmatter fields get added or stripped per provider (`user-invocable`, `argument-hint`, and `license` each present in some copies and not others), and every `{{scripts_path}}`-shaped placeholder gets resolved to that provider's real path. A further rewrite, specific to the `plugin/` subtree (`scripts/lib/plugin-paths.js`), substitutes a host-resolved variable (`${CLAUDE_SKILL_DIR}`) in place of a literal path when a plugin install's cache location can't be known until the host resolves it, and strips the `allowed-tools` key for non-interactive hosts entirely. Same spirit as `pstack-claude`'s `substitutions.json` rewrite rules, implemented as a JS transformer pipeline instead of pattern-matched text substitution — a second real design for the same problem (one skill source, many adapted targets), confirming this is a solved, recurring shape worth having an answer for, not a one-off hack.

**One initial hypothesis was wrong, corrected by reading the actual code rather than guessing from the filename**: `skills-lock.json` is not a content-hash or provenance-integrity manifest the way its name suggests. It's a per-project marker file the CLI uses for project-root detection and to track user-side "pinned" skill shortcuts (`impeccable pin`/`unpin`), unrelated to the generation pipeline. Recorded here specifically so a future reader doesn't repeat the same reasonable-sounding guess.

**A genuinely new procedure-writing device, not seen in any source checked so far**: `skill/SKILL.src.md` tags its own normative sentences with inline HTML-comment rule IDs (`<!-- rule:skill-brief-wins -->`, `<!-- rule:skill-setup-context -->`), apparently so downstream tooling (tests, validation) can reference a specific binding rule by a stable identifier distinct from its prose. The file uses no RFC 2119-style MUST/SHOULD/SHALL keyword convention and no EARS-style trigger syntax anywhere confirmed (a direct, deliberate grep found exactly one incidental hit, not a keyword pattern) — plain imperative English plus ID-tagging is this project's own, different, equally real answer to the same "which sentences are binding" problem RFC 2119 solves with capitalization. Folded into the separate procedural-writing-standards research (`docs/research/2026-10-29-procedural-writing-standards.md`) rather than repeated in full here.

What the subagent could not confirm, stated rather than guessed at: whether `DESIGN.md` documents any writing convention (skipped to stay in budget), whether any of the ~25 `reference/*.md` files use MUST/SHOULD or EARS syntax beyond the one file checked, and whether `bun run build`'s non-release CI invocation performs its own separate staleness diff distinct from the dedicated sync workflow.

## Claude Code's own plugin and skill system: the most mature, most authoritative source audited

Fetched directly from `code.claude.com/docs`: the plugin manifest reference, the marketplace reference, the skills page, and the plugin-evals page — the system this very session runs on, and the origin of the open standard the rest of this audit is built around.

**Claude Code's own skill frontmatter is a superset of the open standard, and Anthropic says so explicitly.** Beyond `name`/`description`, Claude Code's real implementation recognizes `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork` (run the skill in a subagent), `agent`, `background`, `hooks`, `paths` (file-glob activation scoping), `shell`, and `metadata`. The docs state plainly: "The Agent Skills open standard recognizes only `name`, `description`, `license`, `compatibility`, `metadata`, and `allowed-tools`. Fields outside that set cause upload or packaging to fail for claude.ai and the Skills API." That is the open standard's own originator confirming, in its own documentation, that a richer local schema than the portable standard is normal and expected — you pay for it in portability to the strict cross-product surface, not in correctness. This is the clearest confirmation yet that exhaust's own schema (`required`, `gate`, `oracle_mechanism`, `exhaustion_criterion`, `description`/`use_when`/`do_not_use_for`, `eval_fixtures`, none of them in the open standard) is unremarkable, well-precedented practice, not a deviation — exhaust's vertical files were never going to be portable to claude.ai or the Skills API anyway, since they're read by exhaust's own bespoke generator.

**`when_to_use` is a real, separate field in Claude Code's actual schema — not just something ADR 0017 independently reasoned its way to.** The earlier finding in this document called ADR 0017's `description`/`use_when`/`do_not_use_for` split "a deliberate, justified departure" from the open standard's single-field `description`. That's still true against the *portable* standard, but it turns out Claude Code's own real, non-portable implementation already splits `description` from `when_to_use` as two distinct frontmatter fields. ADR 0017 converges with Claude Code's actual schema, not just its own independent reasoning about routing ambiguity.

**Two independent invocation-control flags, not one.** `disable-model-invocation: true` (only a human can invoke, confirmed from `pstack`'s usage earlier in this audit) and `user-invocable: false` (only Claude can invoke, the opposite direction) are both real, separate fields. Together they're a finer-grained version of the idea already flagged as relevant to exhaust's own near-neighbor-routing question (§7.5 of the Playbook proposal): a sub-vertical could be marked unreachable by autonomous model selection, reachable by autonomous selection but not by a human slash-command, or both, depending on how the Harness's own dispatch logic is meant to interact with it.

**Concrete, specific context-budget numbers, more precise than anything else found in this audit.** The startup listing truncates each skill's combined description text at 1,536 characters. An invoked skill's body persists across turns, and compaction re-attaches up to 5,000 tokens per invoked skill, within a combined 25,000-token budget across all currently-invoked skills. These are harder numbers than the open standard's own "~100 tokens" / "under 5,000 tokens" guidance — worth citing directly if exhaust ever needs to defend a specific size budget for a vertical's procedure rather than appealing to vague guidance.

**Discovery is runtime directory scanning here too — confirmed from the format's own originator, at the deepest level of detail in this audit.** Seven distinct scopes (enterprise, personal, project, nested-subdirectory, `--add-dir`, plugin, claude.ai-synced), each scanned live, with a documented precedence order when names collide (enterprise overrides personal overrides project; plugin skills are namespaced so they never collide with anything). The docs state outright that there is no generated or committed index — Claude Code "watches skill directories and picks up added, edited, or removed skills without a restart." This is the single strongest confirmation in the whole audit of this document's main finding: even the system that invented the open standard doesn't use a generated-and-diffed catalog as its actual discovery mechanism.

**`claude plugin validate` is the closest thing to a CI gate found anywhere in this audit — and it's still per-plugin schema/path validation, not a generated-catalog diff.** It checks manifest shape, path existence, path containment (refusing anything that escapes the plugin root or contains `..`), and reserved/impersonating names, with a `--strict` flag that turns warnings into CI failures. This is real, serious tooling — considerably more adversarially hardened than anything else checked in this audit (dedicated impersonation-pattern detection, reserved-name squatting protection, a whole table of validation messages) — but it validates one plugin's own files against its own schema, never a derived, committed, catalog-wide index checked for drift against source. ADR 0016's discipline is still the stricter one.

**`claude plugin eval` is real, mature precedent for exhaust's own `eval_fixtures` field (ADR 0014) — worth modeling against when exhaust actually builds this.** It's explicitly a behavioral/quality eval, not a schema check: a suite of realistic prompts, each graded by regex, tool-call assertions, or a second model's rubric judgment, scored and compared against a no-plugin baseline, with `claude plugin eval init` able to propose cases and graders from a description of the plugin. Teams gate CI on the score. This is a full, working answer to the same problem ADR 0014's `eval_fixtures` field only gestures at today (a pointer to one known-vulnerable and one known-clean fixture per vertical) — a real design to study once exhaust actually builds out its own eval mechanism, not just names the need for one.

**Still zero cryptographic content-signing, even here.** Claude Code's marketplace tooling is the most adversarially-hardened system in this entire audit — reserved official-marketplace names, impersonation-pattern detection on both marketplace and plugin names (including homoglyph/bidi-character and "near-spelling" checks), `sha256` pins on downloaded archives. But that `sha256` is an integrity pin against a known-good hash the marketplace author already chose to publish, not a publisher-identity signature the way ADR 0022 specifies for community-contributed content. Across every single source in this audit, including the one with by far the most serious anti-impersonation engineering, nothing does what ADR 0022 asks for. That ADR's requirement is confirmed, one more time and more authoritatively, as a genuine point where exhaust's own design goes further than the entire field, not an oversight anywhere close to being caught up to.
## Discovery and staleness: exhaust's generator discipline is stricter than everything checked, not behind it

This is the most load-bearing finding for ADR 0016. **None of the nine sources use a generated, committed, CI-checked catalog as their actual discovery mechanism.** Anthropic, Vercel's skills.sh, and Cursor all do runtime directory scanning (2–3 levels deep, with documented shadowing/fallback rules for conflicting locations) — the skill set is whatever the filesystem happens to contain at launch, never diffed against a committed artifact. agentskills.io ships a validator (`skills-ref validate`), but it checks one skill directory's frontmatter at a time, not a catalog-wide index. OpenSpec's closest equivalent, its "verify" step, is a manual or agent-run check that implementation matches spec — not an automated generator, not a CI gate; its own `init`/`update` commands generate derived agent-directory files explicitly described as "never update on their own," i.e., the exact staleness risk ADR 0016 exists to prevent.

The first genuine precedent for exhaust's actual approach came from an unexpected direction: **`intellectronica/ruler`**, a tool solving a structurally similar but different problem (one source-of-truth ruleset, fanned out into every AI tool's own native config format). Its own recommended discipline — regenerate locally, then wire a CI check that reruns the generator and fails the build on any diff against what's committed — is the identical shape ADR 0016 already specifies for exhaust's catalog, arrived at independently for a different artifact.

A stronger, more direct precedent turned up later in this audit (see the dedicated section above): **`michael-denyer/pstack-claude`**'s `tools/generate.mjs --check`, wired into its own CI as a dedicated job, is the same shape applied to a harder problem (an entire translated plugin tree, kept honestly in sync with someone else's upstream forever, not a one-time local build). Between the two, that's real, external validation from two independent projects that generate-then-CI-diff is the correct engineering answer to this class of problem, not a reason to add anything exhaust doesn't already have.

A third project, `pbakaus/impeccable`, solves the identical one-source-many-targets problem but picked the looser of two defensible options: regenerate and auto-commit the drift back to `main` rather than fail the PR (see the dedicated section above). Naming this as a real, deliberate alternative — not a mistake — sharpens rather than weakens ADR 0016's own choice: exhaust's fail-closed CI gate is one of (at least) two legitimate designs for this problem, and it's the stricter one, picked deliberately rather than because the looser one wasn't considered.

A fourth project, `trailofbits/skills`, adds a different, sharper discipline that none of the first three named: its validator scripts ship a `--self-test` mode that builds a deliberately bad fixture and asserts every check actually rejects it, justified by three cited real historical failures where a check silently matched nothing for months and nobody noticed — stated as a named principle, "a checker that inspects zero items must fail, not pass." `exhaust skill lint`'s own test suite already exercises each check against a bad fixture per check (independent convergence, not copied), but doesn't yet have the specific shape Trail of Bits names: a test confirming a check's clean path isn't silently vacuous, as opposed to genuinely passing. Worth a small, concrete addition to `tests/test_skill_lint.py` once there's a second or third real vertical to test against.

**Conclusion for the Playbook's generator**: nothing here suggests changing ADR 0016's design. If anything, it's ahead of every piece of tooling checked, including the open standard's own reference tooling. The two additions worth making are additive, not corrective: adopt the `name`-matches-directory-name rule as a generator-enforced check (not just documented convention), and consider adding the open standard's size guidance (SKILL.md body under ~500 lines / 5,000 tokens, reference chains one level deep) as an explicit lint rule alongside ADR 0017's existing routing-contract lint, since it's the same kind of mechanically-checkable budget discipline ADR 0013 already argues for in prose.

## Sources that didn't add much

**OpenSpec** is a different paradigm (spec-driven development workflow: propose → spec → apply → verify → archive) rather than a skill-distribution format — relevant only for the "verify" step comparison above, nothing in its schema maps onto exhaust's vertical files.

**Google Cloud's page** would not render via fetch (client-side/JS-gated); secondhand sources describe a `google/skills` repo using the same `SKILL.md` + YAML frontmatter shape with `name`/`category`/`description` fields, consistent with everything else found here, but this is explicitly *not* independently confirmed and shouldn't be cited as settled.

## What this doesn't settle

This still isn't the Playbook lock — it's input for when the catalog's schema actually gets finalized, same status as every prior cross-check. Six concrete deltas are now on the table for whenever §2 gets revisited: enforce `name` == directory name in the generator, add a body-size budget check (with Claude Code's own 1,536-character / 5,000-token / 25,000-token numbers as a concrete reference point, not just "keep it short"), weigh whether a `disable-model-invocation`-equivalent flag belongs in the schema for sub-verticals the Harness can dispatch deterministically (the separate procedural-writing-standards research now has a concrete decision rule for this, from Matt Pocock's `writing-for-agents` skill: pick it only when the agent must reach the sub-case on its own, or another skill must — otherwise leave it dispatched by name and pay no extra context load), study `claude plugin eval`'s design (prompt-plus-grader suites, baseline comparison, CI score gate) before actually building out ADR 0014's `eval_fixtures` mechanism, consider a `skill-rules.test.mjs`-style regression test that pins specific hand-written sentences (an exit condition, a routing clause) against silent loss during a future edit, the one gap a schema-only check like `catalog.py`'s `MalformedSkillFileError` structurally can't close, and add a zero-findings-must-not-silently-pass test to `test_skill_lint.py` per `trailofbits/skills`' named principle. Everything else in exhaust's existing design is confirmed sound against fourteen live-checked sources, not merely unchallenged — including four independent real-world instances of the exact staleness problem ADR 0016 exists to solve (one caught drifting with no generator at all, one solved by the strongest fail-closed precedent found in this audit, one that solved it with a deliberately looser auto-commit policy worth naming as a real alternative rather than a mistake, and one that adds a validator-self-test discipline none of the first three named), and the confirmation, from the open standard's own originator, that exhaust's own richer-than-portable schema and ADR 0022's signing requirement are both normal, well-precedented engineering, not oversights to correct.
