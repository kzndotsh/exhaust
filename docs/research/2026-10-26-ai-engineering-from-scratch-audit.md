# Audit: rohitg00/ai-engineering-from-scratch

Source: [github.com/rohitg00/ai-engineering-from-scratch](https://github.com/rohitg00/ai-engineering-from-scratch), a 542-lesson AI/LLM engineering curriculum (74,350-plus stars, actively maintained, MIT) and the repo backing this session's own `ai-engineering-from-scratch` skill. Audited for its agent-skills and agent-security lesson content specifically, not as a tool. Read directly via a shallow, blobless clone and a targeted read of `skills/learn-agent-skills/SKILL.md` and `phases/13-tools-and-protocols/26-skill-permissions-sandboxes-and-trust/docs/en.md`, not via subagent fan-out.

## Adopted: a five-layer control taxonomy that independently validates exhaust's own separation of concerns

Folded into [ADR 0003](../adr/0003-scope-contract-gates-real-targets.md). The curriculum's own skill-security lesson decomposes agent-tool risk into five genuinely distinct layers: **capability exposure** (can the agent request the operation at all), **permission policy** (is this actor allowed for this target), an **approval gate** (did an authorized party accept this specific consequence), a **sandbox** (what can the executing code actually reach), and a **verification gate** (did the result meet the contract). It states, in these words, that a runtime's own tool-allowlist setting is capability or permission prompting, never operating-system isolation, and does not by itself stop an allowed tool from reaching an unintended path. This is a clean, independently-arrived-at confirmation that exhaust is right to keep its Scope Contract (permission policy), its Sandbox (execution isolation), and its Oracle (the verification gate, ADR 0008) as three separate mechanisms, none of which can substitute for the others, and names precisely the shortcut (a bare tool-allow list) that every audited tool in this research project that failed its Scope Contract audit actually took instead.

## Reinforced, not new

**A fallback path must never be recorded with the same status as a verified one.** The curriculum's own Agent Skills lesson route is explicit about this: when a real-lab precondition can't be established (a missing runtime, an unavailable host), the lesson continues conceptually but every checkpoint that would have required the real run is marked `Pending`, and the route's own instructions say outright, "never describe that fallback as a real checkpoint." This is the same distinction already settled in [ADR 0005](../adr/0005-harness-done-is-a-per-vertical-ledger.md) ("errored is not exhausted"), arrived at independently in a teaching context rather than a security one, and a useful precise phrase ("never describe a fallback as a real checkpoint") for the exact discipline exhaust's own per-vertical ledger needs to hold.

**Routing-contract-style skill descriptions, now seen in a third independent source.** The curriculum's own `SKILL.md` front matter opens its description with exactly the shape already settled in [ADR 0017](../adr/0017-skill-descriptions-carry-a-routing-contract.md): a one-line statement of what the skill is for, followed by an explicit "start or resume this route when a learner wants to [enumerated list of intents]" clause. No change to the ADR; one more independent source converging on the same shape.

## What this settled for exhaust
