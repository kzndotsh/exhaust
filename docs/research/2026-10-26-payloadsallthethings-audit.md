# Audit: swisskyrepo/PayloadsAllTheThings

Source: [github.com/swisskyrepo/PayloadsAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings), cloned shallow for this audit. "A list of useful payloads and bypass for Web Application Security and Pentest/CTF." A massive, well-known, community-curated reference of per-vulnerability-class technique docs, pure content, with no harness or tool to speak of. Audited specifically for spine content, not architecture: its per-class template, and how its roughly 64 categories map onto our 11-vertical spine candidate, filling or failing to fill the gaps earlier audits (Cloudflare, Anthropic-Cybersecurity-Skills) already flagged. Read-only, read by three subagents.

## Content conventions worth keeping, none rising to a decision

The per-class template here is actually weaker than what we've already decided (no detection-versus-exploitation split, no "when to use this" trigger text, no verification step), which is itself useful confirmation that ADRs 0011, 0013, and 0017 are already ahead of this reference rather than something to catch up to. Three small, genuinely useful conventions worth carrying into whenever skills get written: a citation format requiring author, title, date, and an archived link for anything referenced; a payload-hygiene discipline (placeholders like `[ATTACKER.DOMAIN.TLD]`, using `id`/`whoami` as an RCE proof rather than anything destructive); and a simple Tools-list format (`[owner/repo](url) - description`).

**Guidance for the known-CVE vertical, from a negative example.** This repo's own `CVE Exploits` category is a hand-curated list of seven narrative writeups with no systematic product-to-version-to-CVE index, and it points to real machine-readable sources instead (CVE feeds, nuclei-style detection templates) as the actual way to scale. The lesson: don't hand-curate a CVE narrative list; keep a local artifact keyed by detected product and version, and link out to a maintained feed for the actual lookup.

## Spine-content material, organized for whenever the spine gets locked

**Four categories map cleanly onto existing verticals.** IDOR into access control, SSTI into injection, race conditions into logic flaws, insecure file upload directly into file handling.

**Three split across more than one vertical rather than needing their own.** GraphQL spans injection (its NoSQL/SQL sections), info disclosure (introspection and schema enumeration), and access control (batching as a rate-limit bypass); it may deserve one dedicated entry if API-specific testing matters enough to the spine, given how much content it carries on its own (nearly 500 lines in this source alone). Web Cache Deception splits between info disclosure (caching sensitive responses) and an infrastructure-adjacent cache-poisoning half. WebSockets splits between an auth/session-shaped issue (cross-site WebSocket hijacking, since cookies ride along automatically) and an injection-shaped one (message-level fuzzing).

**One category is genuinely homeless, and it shares a root cause with two others.** HTTP request smuggling, a front-end/back-end parser disagreement, doesn't fit anywhere in the current 11 verticals, not injection, not CSRF, not client-side. Worth noting directly: this source observes that request smuggling, web cache deception, and part of the WebSocket surface all come from the same underlying class of problem, a proxy or cache disagreeing with the origin about how to parse a message. That's a real candidate for a single small vertical (something like "proxy and transport parsing discrepancies") rather than three separate unresolved cases, though whether it earns a slot is the spine-locking decision's call, not this audit's.

**Categories with no home at all in the current spine, beyond what was already flagged.** Prompt injection is the clearest novel gap, an LLM-specific input-manipulation class nothing in the spine touches; worth connecting to the still-open question from the OWASP ASRH audit about whether exhaust ever tests a Target that itself embeds an LLM, and separately whether exhaust's own Harness needs a self-test suite against the same class of attack. Denial of service and ReDoS (availability and algorithmic-complexity testing), DNS rebinding and virtual-host attacks (network/routing-layer, not covered at all), supply-chain concerns (dependency confusion, exposed API keys, insecure source-code management), and brute-force/rate-limiting as a standalone control (rather than a side effect of testing auth) are all real gaps with no natural home in the current 11.

**One composite worth naming as a pattern, not a vertical.** Account takeover isn't a distinct technique class; its own content decomposes almost entirely into auth/session and access-control primitives already in the spine (password-reset flaws, weak tokens, MFA bypass, IDOR on reset endpoints). What it contributes is a chained, goal-oriented test plan across primitives the spine already covers, which may be worth keeping as a worked example of how to chain verticals toward a business outcome, not as its own entry.

## What this settled for exhaust

Nothing architectural; no new ADRs. This is organized reference material for the spine-locking decision: four clean fits, three split-fits, one genuinely homeless category that may be worth its own small vertical, and several real gaps (prompt injection, DoS/ReDoS, DNS/vhost attacks, supply chain, rate-limiting-as-a-control) with no current home, to weigh alongside everything the Cloudflare and Anthropic-Cybersecurity-Skills audits already surfaced.
