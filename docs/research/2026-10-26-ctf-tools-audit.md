# Audit: zardus/ctf-tools

Source: [github.com/zardus/ctf-tools](https://github.com/zardus/ctf-tools), "Some setup scripts for security research tools." Checked via a blobless clone and targeted tree listings rather than a full multi-agent audit, since the repo is narrow and specific: a Nix flake packaging roughly fifty CTF and security-research tools (binary analysis, crypto, web, steganography, forensics), one derivation per tool, with daily CI builds and a binary cache.

## The strongest, most directly reusable confirmation of ADR 0012 found in this research

This repo is close to a working implementation of what [ADR 0012](../adr/0012-rig-wraps-a-pinned-tool-catalog.md) already calls for, in the exact ecosystem your own lab module already uses. Each tool is its own Nix derivation (`nix/pkgs/<tool>/default.nix`), pinned to an exact version and source hash, with real engineering judgment recorded in comments where it matters (the `pwndbg` package, for instance, deliberately skips Nix's usual binary-patching step because the vendor's own portable bundle carries its own loader, and patching would fight it). A thin CLI (`manage-tools`) wraps `nix profile install/remove/upgrade` with familiar verbs (`install`, `uninstall`, `upgrade`, `search`, `list`), so the whole thing presents as a simple tool manager while being Nix underneath. CI evaluates and builds the entire catalog daily, publishing to a binary cache so a user gets a prebuilt result instead of recompiling.

Two things worth calling out specifically as mechanisms to borrow or even reuse directly. First, different parts of the catalog are deliberately pinned to different upstream snapshots where that's what correctness requires: a separate, frozen nixpkgs input exists purely to keep certain cross-compilation toolchains stable, and another pinned-older input exists specifically to keep Python 2.7 and its package set buildable for the handful of legacy tools (`volatility`, `featherduster`, `qira`) that still need it, rather than stubbing them out. That's a concrete pattern for exhaust's own Rig catalog once it needs to carry tools with genuinely different dependency lifecycles. Second, the catalog includes tools directly relevant to exhaust's spine that weren't flagged in prior audits: `pwndbg`, `ida-pro-mcp` (an MCP server driving IDA Pro, a different approach from REA's own bridge), `decomp2dbg`, `manticore`, `qiling`, and `libc-database`, among others.

Given how directly reusable this is, the concrete recommendation is to treat this flake as something exhaust's own Rig could depend on or fork from outright, rather than building an equivalent pinned-tool-catalog mechanism from scratch, since the hard parts (per-tool pinning discipline, CI verification, a binary cache) are already solved and already live in the ecosystem the lab module already commits to.

## What this settled for exhaust

Nothing new decided; [ADR 0012](../adr/0012-rig-wraps-a-pinned-tool-catalog.md) already covers this and this repo is the strongest evidence yet that the decision is both right and already implementable with existing, maintained infrastructure rather than something to build from first principles.
