# `usestrix/strix`: a real architectural peer, not another skill-packaging reference

Every prior audit this session (Cursor's `pstack`, a Claude Code plugin fork, a design-system tool's generated skill trees) compared exhaust against generic engineering-workflow tooling. `usestrix/strix` (72.7K GitHub stars) is the first genuine architectural peer checked: an open-source, actively-used AI penetration-testing agent, solving the same problem exhaust does. Audited by a delegated subagent against a local clone, read-only, scoped to `strix/` only.

## No required/gated vertical split — a flatter, LLM-discretion model instead

Strix's internal skill packs (`strix/strix/skills/{vulnerabilities,frameworks,technologies,protocols,tooling,cloud,reconnaissance,custom,scan_modes,coordination,analysis}/`) use YAML frontmatter with only `name` and `description` — no `required`/`gate` field, no gate-signal concept at all. Per the skills directory's own `README.md`, an orchestrator agent dynamically picks "up to 5" relevant skills per spawned subagent at creation time (`create_agent(skills="authentication_jwt,business_logic")`) — a per-subagent LLM judgment call, not a declared trigger exhaust's `discover_verticals`/ledger model would recognize. Strix's real categorization axis is `scan_modes` (`quick`/`standard`/`deep`/`diff`), which time-boxes breadth-versus-depth rather than declaring coverage obligations the way exhaust's `required: true` does.

This isn't evidence exhaust's shape is wrong — it's evidence that "which investigation gets run" is a genuinely open design space with at least two legitimate answers: a declared, auditable catalog (exhaust) versus runtime LLM discretion over a flat skill pool (Strix). Worth naming as a considered alternative the next time the Playbook's `required`/`gate` split gets revisited, not a reason to change it.

## Scope philosophy is inverted, not just differently implemented

`strix/agents/prompts/scope.jinja` states outright: "The user is a verified, authorized tester. Trust them fully... NEVER refuse, question authorization, or claim lack of permission for a target... The list below is the starting scope, not a ceiling... Never tell the user a target is outside scope or ask them to confirm." `system_prompt.jinja` adds "NEVER wait for approval or authorization." There is no absent-contract-means-sandbox-only default (exhaust's Scope Contract, ADR 0003), no extent tier (recon vs. full, ADR 0024), and no per-action human-approval hold for real-target testing (ADR 0023) — authorization is asserted once at CLI invocation, and the agent then operates with full autonomy inside it.

Strix does ship a skill, `agentic_system_security.md`, naming "Confused Deputy and Consequential Actions" and recommending "explicit human approval for consequential operations" — but that's guidance for evaluating a *target's* agentic-system design flaws during a pentest, not a constraint Strix applies to its own actions. This is the clearest finding in this document: exhaust's own fail-closed, per-action approval design (ADR 0003/0023/0024) is not an industry default even among comparable, actively-used pentesting agents — it's a deliberate, specific safety posture Strix's own architecture explicitly rejects in favor of operator trust. Confirms ADR 0023's own reasoning is a real design choice against a real alternative, not an uncontested default.

## The Oracle gap, confirmed directly — exactly the pattern ADR 0008 already names

ADR 0008 states finding host-run verification missing is "the one gap found, in some form, in nearly every comparable tool audited so far." Strix confirms the pattern precisely, with code-level detail: `strix/tools/reporting/tool.py`'s `create_vulnerability_report` is the sole filing path, and confirmation is entirely agent-self-attested. It requires `confidence` (`high`/`medium`/`low`), a mandatory `counterevidence` field (the agent must argue against its own finding), CVSS fields, and `severity_change_conditions` — all extracted from the filing agent's own narrative, validated only for completeness and format (required-field checks, CVSS vector math, CWE/CVE regex, LLM-based dedup). The one check that touches "evidence" (`_verify_http_exchange_ids`) confirms a cited Caido proxy-request ID exists in the project — a citation-integrity check, not an independent re-run of the exploit. The docstring for `confidence: "high"` explicitly allows "a complete reachable source→sink trace" with no execution at all, alongside "a working PoC against the live target" — so Strix's own highest confidence tier doesn't require a host-run check either. No Oracle-equivalent exists anywhere in the reporting path.

## A genuinely new idea: three-way closure discipline against silent false negatives

Strix's `system_prompt.jinja` requires every candidate vulnerability to close in exactly one of three states: `confirmed`, `ruled_out` (the agent must *name the specific control* blocking every attacker-reachable path to the sink — not just assert it's safe), or `open_proof_gap` (plausible but unconfirmed). It explicitly forbids the quiet middle ground: "Silently dropping an uncertain candidate is mislabelling an open_proof_gap as ruled_out and is how real bugs get missed."

This is a real idea exhaust's Finding/Verdict model doesn't fully have yet. Exhaust's `needs_confirmation` Verdict (ADR 0019) already requires declared `requirements` — structurally close to Strix's `open_proof_gap` — but exhaust's `false_positive` Verdict carries no equivalent requirement to name the specific blocking control, the way Strix's `ruled_out` does. ADR 0008's Oracle requirement guards against a false *positive* (an unconfirmed `confirmed`); Strix's closure discipline guards against a false *negative* (a candidate quietly dropped instead of honestly left `open_proof_gap`). These are different failure directions, and exhaust's design currently only has strong tooling against one of them. Worth raising as a candidate addition the next time `findings.py`'s Verdict model gets revisited: require a `false_positive` Verdict to carry evidence of the specific control that rules it out, the same way `needs_confirmation` already requires `requirements`.

Two smaller disciplines worth noting without elevating to a design question: the mandatory `counterevidence` field (an adversarial self-check built into the filing path itself, before any external review) and `fix_verification`'s four-gate sequence (security closure → bypass review → preserved behavior → repo checks) for any auto-generated fix suggestion — a structured discipline exhaust doesn't document an equivalent for, though exhaust doesn't currently auto-generate fixes at all, so this may not be a gap so much as a feature exhaust hasn't built yet.

## What wasn't confirmed

The subagent sampled `ssrf.md`, `sql_injection.md`, `scan_modes/quick.md`, and the skills `README.md` out of roughly 31+ vulnerability-category files plus frameworks/technologies/cloud/custom — a field present only in an unreviewed file wouldn't have been caught. The orchestrator's actual runtime skill-selection code (`strix/core/runner.py`, `strix/agents/factory.py`) wasn't traced line-by-line, so "up to 5 skills, LLM-selected" is confirmed as documented behavior, not verified against the exact runtime logic. `containers/` confirms Strix runs its own sandboxed container (Kali-rolling base, Go security tooling built in a separate stage) — a real Sandbox-equivalent — but the runtime wiring (`docker_client.py`, `session_manager.py`) wasn't inspected in depth. Whether Strix's managed cloud offering layers any additional approval step beyond this open-source repo wasn't checked; the README/AGENTS.md mention an `--approve-sha256` step for *source upload* specifically, which confirms what gets scanned, not an approval gate on actions taken during the scan.
