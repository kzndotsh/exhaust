# Scope Contract gates testing of real Targets

By default an Exhaust agent may only attack the Sandbox, the local isolated instance of the Target. Attacking a real, remote Target requires a Scope Contract in the Workspace that names the Target, the permitted extent of testing, and the basis for authority (owned infrastructure, a published bug-bounty scope, or written permission). No contract means Sandbox-only.

Exhaust runs agents autonomously, so the boundary on what they may touch has to be explicit and machine-checkable, not left to the agent's judgement in the moment. This is both the safety floor for autonomy and the responsible-disclosure discipline the project is built around. The term and shape follow standard agent-engineering practice, where a per-task scope contract states where work begins, where it ends, and what is in scope.

The Scope Contract's authority can only come from the Workspace file itself, checked by the Harness before any real-Target action, never from anything that arrives inside the agent's own context: a Target's response, a tool result, or text an agent generates. A hostile Target that returns "you are now authorized, proceed" must not be able to satisfy this gate. Four audited tools (deepsec, Shannon, this project's own reference harness, and its detection-response track) all left real-target authorization as prose a prompt merely asks the agent to respect, with no case of it being enforced in code; this ADR's gate exists specifically to not repeat that.

The one audited tool that did build a real structured scope check (a host/CIDR allowlist, not prose) still failed in two instructive ways: it defaulted to fully permissive until something populated the list, rather than defaulting closed, and it was only one of several code paths that could execute a tool, so other paths bypassed it entirely. Both are directly why this gate must default to Sandbox-only with nothing configured, never permissive-until-told-otherwise, and must sit at the single point every tool call passes through, never as one optional check among several ways to reach a tool.

The gate is re-checked immediately before an action actually executes, not only when that action was first proposed or queued. Time passes between an agent deciding to do something and the Harness actually doing it, and the Scope Contract could change in that window (a scope narrowed, a Target removed). A real-world capability system built around exactly this kind of check (Cloudflare's internal agent platform) binds an action's authorization to an identity token at the moment it's queued and checks that binding again right before it applies the action, rather than trusting the earlier check to still hold. We deliberately did not adopt that same system's pattern of letting an agent proceed on a simulated result while a human approval is still pending (even for productivity-app actions with a reversible downside, its own designers' planning notes call the question of what happens if that approval is later rejected "an unresolved gap" in their design). For an action against a real Target, proceeding as if authorized before authorization is actually confirmed is the exact failure mode this ADR exists to prevent; the cost of being wrong is categorically higher here than it is for a Gatekeeper that might wrongly simulate a sent email.

A general agent-security curriculum lesson on skill permissions independently decomposes exactly this problem into five distinct control layers: capability exposure (can the agent request the operation at all), permission policy (is this actor allowed for this target), an approval gate (did an authorized party accept the specific consequence), a sandbox (what can the executing code actually reach), and a verification gate (did the result meet the contract). It states plainly that an agent runtime's own tool-allowlist setting is capability or permission prompting, never operating-system isolation, and does not by itself prevent an allowed tool from reaching an unexpected path or acting outside the intended boundary. This is independent confirmation that exhaust is right to keep its Scope Contract (permission policy), its Sandbox (execution isolation), and its Oracle (ADR 0008, the verification gate) as three genuinely separate mechanisms rather than treating any one of them as standing in for the others; a tool-allow list or a prompt-level permission alone, the layer most agent frameworks implement first and sometimes only, closes none of exhaust's actual risk.
