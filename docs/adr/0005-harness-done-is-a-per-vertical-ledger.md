# The Harness's "done" is a per-vertical ledger, not a heuristic

Each vertical in a Workspace's Playbook carries an explicit state: `pending`, `in_progress`, `retryable`, `blocked`, or `terminal` (`exhausted` or `skipped`). A vertical reaches `terminal` only when either its gate excluded it (logged with a reason) or the agent has worked it to completion and explicitly attests, via a forced self-report turn, that it has no further avenues. The Workspace is done when every vertical is terminal. A cost or duration budget can halt a run with verticals still in progress; because state is explicit, the next run resumes exactly those.

We looked at vercel-labs/deepsec's scanner for comparison and found it has no real completion condition: a scan is "done" once every matcher has run once, measured only by a weak match-rate-per-language heuristic its own code comments flag as unreliable. That is the opposite of what an agent-first autonomous tool needs. Exhaust's entire premise is that the Harness keeps the agent going until the methodology is actually exhausted, so "done" has to be a real, auditable ledger (which verticals were exhausted, which were skipped and why, which were cut short by budget), not a side effect of having run once.

One more failure mode a ledger must guard against, found elsewhere: a vertical that errored or was rate-limited partway through must never read as "exhausted, nothing found." A clean result and a silently-failed one look identical unless the ledger records which happened, so this needs its own state, distinct from both `exhausted` and `skipped` — and it needs to further distinguish a known, resumable failure from a real-Target action left with an ambiguous outcome, which has to block rather than silently retry (see [ADR 0015](0015-crash-mid-real-target-action-blocks-not-retries.md)). That split is `retryable` (safe to pick back up automatically) versus `blocked` (a person has to look before this vertical moves again).

A fifteen-year-old, unrelated system-hardening auditor (Lynis) arrived at the same mechanism independently: one registration function is the single choke point every check passes through, which is where its identity and its run-or-skip decision get recorded with a reason, and a "not run" outcome is as first-class as a pass or fail. Any score or report the system produces is scoped only to what actually ran. That's the concrete shape this ADR's ledger should take: one function the Harness calls to enter a vertical into the ledger, not scattered bookkeeping across wherever a vertical happens to start or stop.

One more lesson, from the most popular tool in this space: having the right vocabulary for closure is not the same as the harness enforcing it. That project's own agents close each surface as `confirmed`, `ruled_out` (naming the specific control that rules it out), or `open_proof_gap`, almost exactly the ledger states this ADR calls for, and its own documentation describes exactly when each applies. But the code never reads any of it: its finish tool checks only that no child agents are still running, never that the coverage ledger's entries actually meet their own stated bar, and an agent can end its run with open items the harness never inspects. The vocabulary lived entirely in the prompt, not in anything the Harness itself validated. The lesson is specific: whatever ledger exhaust builds, the Harness's code must be the thing that reads and checks each entry before accepting a vertical as terminal, never merely the thing that asked the agent to produce the right words.
