# A `confirmed` Verdict requires a host-run Oracle, not just the agent's say-so

A Finding may only be marked `confirmed` once an Oracle, a host-executed check independent of the investigating agent, has replayed its evidence against the Sandbox and verified the claimed effect actually occurs. An agent's own report that it reproduced something is not sufficient on its own.

Anthropic's own reference vulnerability-discovery pipeline does not do this: despite compiling ASAN into every target, its discovery stage's "crash_found" status is entirely an LLM grader reading its own prose tags, with nothing on the host re-executing the proof-of-concept at that point. The only place that pipeline enforces anything mechanically is a separate patch-validation ladder, not discovery itself. Combined with the same gap found in deepsec (no scored evaluation at all) and Shannon (the "no exploit, no report" tagline is a self-attested enum, not an independent replay), this is now a pattern across every audited tool: self-attestation is treated as proof when it is only a claim. The one place any audited tool solves this correctly is the reference repo's own detection-and-response track, where the scoring ground truth is mounted read-only inside a fresh container the investigating agent never sees. That is the shape an exhaust Oracle should take: independent, run by the host or a separate process, with no access to the agent's reasoning or session.

The most widely used tool in this entire space (72,000-plus stars) markets itself specifically on having solved this, in exactly these words: "real exploit validation - working PoCs, not false positives like legacy vulnerability scanners." Reading its code closely finds no host-run re-execution anywhere in the pipeline: a finding's required "PoC script" field is stored and rendered to reports as text, never parsed or executed by anything; its "independent verification" step is just another LLM agent session reading the same claim with a different context window, not a separate execution path; the one check against anything external (that a cited proxy-traffic ID exists) confirms the ID is real, not what the traffic actually showed. The claim is marketing language the implementation does not back up. This is the strongest evidence yet, from the single most prominent tool audited, that building a real Oracle is not merely good practice but a genuine, unsolved gap nobody else in this space has actually closed, whatever they advertise.

An independent code-level teardown of five autonomous pentest agents (including two already audited here) reached the same conclusion across all five, and named the concrete mechanisms that would actually close the gap, since none of the five implements any of them: an out-of-band callback (the Target makes a request to an attacker-controlled collaborator domain, and the collaborator receiving that hit is unforgeable from inside the agent's own transcript); a control-versus-injected differential (the same request sent twice, once with the payload and once without, with a measurable divergence in the response); an observed execution signal for client-side bugs (confirmation that injected script actually ran, not merely that it appears reflected in a response body); and a cross-session access differential for authorization bugs (one user's credential successfully reading another user's data, checked by actually making both requests, not by the agent's own account of what it saw). These four are exhaust's Oracle's concrete starting toolkit: each is cheap to implement, each is verifiable without re-litigating the agent's reasoning, and between them they cover the overwhelming majority of what a web-application Finding needs confirmed.

A fifth mechanism, from a widely used LLM vulnerability scanner in an adjacent domain: an independent-ground-truth differential, where a claim extracted from the Target's own output is checked against a separately sourced, versioned corpus the Target has no influence over, rather than trusted at face value. That project's package-hallucination detector extracts an imported package name from a model's generated code and checks it against a dated snapshot of what packages genuinely existed on the real package registry at that point, rather than asking the model whether the package is real. The same shape applies directly to exhaust: a claimed CVE ID, exposed package version, or known-vulnerable component should be checked against a real, independently sourced registry or advisory feed, not accepted because the agent or the Target's own banner says so.
