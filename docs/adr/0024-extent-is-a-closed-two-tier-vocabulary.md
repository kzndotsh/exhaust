# A Scope Contract's extent is `recon` or `full`, not free text

`ScopeContract.extent` becomes a closed, two-value vocabulary, `recon` or `full`, instead of the free text it's been since ADR 0003. `full` authorizes everything `recon` does, plus anything else; `recon` authorizes only passive, non-mutating, non-intrusive testing. A Rig bridge declares which tier each of its methods requires, the same way it already declares `consequential` (ADR 0023) and `mutates`, at its own enumerated method registration. `is_in_scope` takes that requirement as a parameter and checks it against the contract's tier alongside the target match it already does; a contract whose `extent` isn't one of the two known values fails closed, the same as an unknown `basis` already does.

Until now, `extent` was loaded, required to be a non-empty string, and then never read again: `is_in_scope` only ever compared `target`. A contract could say `extent: read-only recon only` and a fully destructive `RealTargetCall` would still pass, because nothing checked the field a human wrote specifically to bound what testing was authorized. That's not a theoretical gap; it's dead code enforcing nothing, found by reading `scope_contract.py` directly. Free text can't be enforced against a proposed action without parsing prose, so closing the vocabulary is the only way to make the field do what it was always meant to.

Two tiers, not more, for now. A recon/active/exploit split, or further tiers for post-exploitation or persistence, would track how real penetration-test rules of engagement are usually written, and may be worth adding later. Starting there would mean guessing at a vocabulary before any real Rig tool exists to need it, the same caution this project already applies to the pinned-tool catalog and the vertical catalog: don't lock in a shape nothing yet demands. Two tiers, ordered so the larger implies the smaller, is the smallest version that still does real work, covers the one distinction the project has needed language for so far (read-only vs. let-it-actually-act), and is cheap to extend later without re-opening the mechanism itself, only the set of values it checks against.

The requirement lives on the Rig side as a plain string, not as a shared enum type, because `rig` and `scope_contract` are independent domain modules (`import-linter` enforces this) and neither may import the other. `scope_contract.py` owns the two-value vocabulary privately and validates both the contract's own `extent` and whatever string a method declares against it; nothing outside that module ever needs the enum itself, only agreement on the two string values, the same convention `tool` and `method` names already rely on elsewhere in this codebase.
