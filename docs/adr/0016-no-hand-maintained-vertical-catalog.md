# No hand-maintained vertical catalog, separate from the skill files themselves

Whatever lists the Playbook's verticals for a Workspace (for the ledger, for a status display, for anything that needs to enumerate what exists) is computed by reading the skill files directly, never kept as a second, separately-maintained index file that's supposed to mirror them. Concretely: each vertical's `required` and `gate` fields (see [ADR 0011](0011-playbook-verticals-are-required-or-gated.md)) live in that vertical's own skill file, and the generator this ADR requires reads them from there, never from a copy.

Lynis, a system-hardening auditor with roughly 460 individually registered checks, kept exactly this kind of secondary index (`db/tests.db`) alongside its real source of truth (the inline registration call in each check's own code). After years of maintenance it drifted: 34 checks that exist in code are missing from the index, and 5 entries in the index point at checks that no longer exist in code. The audit engine itself never even reads the stale file; only a display helper does, so the drift is invisible until someone goes looking for it. A second, hand-maintained list of the same facts the first list already declares is pure liability: it can only go stale, never catch itself doing so, and exhaust should not create the equivalent for its own Playbook.

Deriving the catalog isn't enough on its own; the generator has to be a real, committed, checked artifact, or the same drift returns wearing a disguise. A library of 818 cybersecurity skills does exactly half of this right: its main catalog file has a committed generator script, a CI check that fails a pull request if the file is out of sync, and a self-healing commit on merge, which is the concrete shape to copy. But several of its other documents (a coverage report, technique-mapping files) claim in their own text to be auto-generated from a script that is listed in `.gitignore` and does not exist anywhere in the repository history. Those documents disagree with each other and with the README on basic counts, with nothing catching it, because the claim of being generated bought them unearned trust with no actual mechanism behind it. A document that says "generated" and isn't checked is worse than one that honestly says "hand-maintained," since the first invites exactly the trust the second doesn't. Every derived view exhaust produces needs its generator committed in the same repository and checked in CI, not merely asserted in prose.
