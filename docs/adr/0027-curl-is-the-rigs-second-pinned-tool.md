# curl is the Rig's second pinned tool, wrapped as two payload-submission methods

The Rig's pinned catalog (ADR 0012) gets a second real entry: curl, pinned at `8.22.0` from `github.com/curl/curl`. The version was confirmed by evaluating `flake.nix`'s own already-pinned nixpkgs commit directly (`nix eval --raw "github:NixOS/nixpkgs/<commit>#curl.version"`), the same real-provisioning-not-changelog-guess discipline ADR 0026 settled on for nmap after an initial mismatch there — this entry doesn't repeat that mistake, since the actual commit was checked before the version was written down anywhere.

This tool exists to close a gap the `injection` vertical's own skill file named explicitly the day it was written (`skills/injection/SKILL.md`, "Known gaps"): nmap's two methods are read-only recon, and nothing in the Rig could submit a value to a Target's input at all. `CurlBridge` exposes exactly two methods, `get` and `post_form`, both declared `mutates=True, consequential=True, required_extent="full"` (ADR 0023, ADR 0024) — the opposite classification from nmap's recon-tier, non-consequential pair, because submitting an attacker-chosen value to a live endpoint is not recon by any definition this project uses, whatever that value turns out to contain. A method whose entire purpose is carrying caller-supplied payloads to a real Target gets the strictest gate the Rig has, by default, not as an afterthought.

The validation shape is the same defense-in-depth ADR 0018 already asks every bridge for, applied to a harder case: nmap's bridge validates a `host` it expects to be *safe* and refuses anything that looks like a flag; `CurlBridge` validates a `url` the same way (no leading `-`, no shell metacharacters, refused before `curl` ever runs) but is explicitly built to carry *unsafe*, attacker-shaped values through in its query parameters and form fields, since that is the entire point of an injection-testing tool. The distinction that keeps this safe: every submitted value reaches `curl` as its own argv token — `--data-urlencode key=value` for form fields, a hand-percent-encoded query string built in Python for `get` — never concatenated into a shell string or passed where `curl`'s own option parser could read it as a second flag. A value like `"'; DROP TABLE users; --"` is exactly the kind of payload this bridge exists to deliver intact to the Target; it is never a payload this bridge's *own* invocation of `curl` can be tricked by, because it never occupies a position `curl`'s argument parser treats as anything but inert data.

Verified against the real binary, not only a fake script a test substitutes for it: `CurlBridge().installed_version()` reported `8.22.0`, matching the pin exactly, and a live `get` against `https://example.com/` returned a real response body. `skills/injection/SKILL.md`'s "Known gaps" section has already been updated to name `curl.get`/`curl.post_form` as real methods and to name the three input shapes (headers/cookies, uploaded filenames, path segments) that still have no Rig method — a direct follow-up this entry carried out, not a separate open decision.

What this doesn't settle: Response-header capture (`-D -`) and a tunable timeout per call were deliberately left out of this first cut, narrower than they could be, in favor of the two methods the injection vertical's own written procedure actually calls for right now (ADR 0018's narrow-enumerated-surface discipline cuts both ways: add a method when a real procedure needs it, not preemptively). Which vertical, if any, needs a third Rig tool next remains open.

**Resolved**: every request now carries a browser-shaped `User-Agent`, `Accept`, and `Accept-Language` header set by default, after auditing `lwthiker/curl-impersonate` (7.1K stars) for ideas. That project's own stated motivation is the real risk here: a plain `curl` invocation's default `User-Agent: curl/<version>` and missing `Accept` header are among the cheapest signals a Target's bot-detection checks for, and a blocked or differently-served response would confound "this Target's WAF filtered a non-browser client" with "this input isn't vulnerable" — exactly the kind of silent confound the Strix-audited closure discipline (`skills/injection/SKILL.md`'s own Exit condition) exists to catch. Confirmed live against `httpbin.org/headers`: the Chrome-shaped headers arrive exactly as sent, `curl`'s own default signature never leaves the binary. What this doesn't adopt: `curl-impersonate`'s deeper technique, a complete TLS/HTTP2 fingerprint match (a custom curl build against NSS or BoringSSL instead of OpenSSL, patched cipher-suite and TLS-extension ordering, non-mainline flags like `--tls-permute-extensions` and `--cert-compression`) — that needs pinning an entirely different, non-mainline binary with its own build and provisioning story, a meaningfully bigger decision than a default header set, and one with no evidence yet that header-level realism alone is insufficient for any real Target.

**Resolved**: the three input shapes named above as having no Rig method (headers/cookies, uploaded filenames, path segments) now all do. `get` and `post_form` both gained an optional `headers` parameter (a cookie is just a header, so one mechanism covers both), `get` gained an optional `path_segment` parameter appended to the URL raw and unencoded — path-segment injection's whole point is controlling the encoding, so this bridge doesn't impose one — and a new third method, `post_multipart`, covers uploaded-filename injection: it writes caller-supplied `content` (never an arbitrary local file path, which would be a very different and much riskier capability) to a throwaway temp file, then uploads it via `curl -F field=@tmpfile;filename=<attacker-controlled>`, so only `filename` is the injection point, never the bridge's own access to the filesystem. All three closed with the same ADR 0018 defense-in-depth the original two methods already used: every value still reaches `curl` as its own argv token, `path_segment`'s raw passthrough doesn't change that since the `--` separator already stops it from being read as a flag. Verified against a real server, not only a fake script a test substitutes for one: a live `post_multipart` against `httpbin.org/post` round-tripped real file content under the given field name. `skills/injection/SKILL.md`'s "Known gaps" section is gone — nothing is blocked anymore — and its Procedure now names which method dispatches which input shape directly, instead of carrying that mapping only in a gaps note.
