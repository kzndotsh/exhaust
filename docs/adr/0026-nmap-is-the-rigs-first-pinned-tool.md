# nmap is the Rig's first pinned tool, wrapped as two recon-tier methods

The Rig's pinned catalog (ADR 0012) gets its first real entry: nmap, pinned at `v7.992` from `github.com/nmap/nmap`, the exact tag confirmed against the project's own release history rather than assumed from a locally installed copy or a training-data guess. Until now `PINNED_TOOLS` was deliberately empty and its own module docstring said so explicitly; this closes that specific open question without reopening ADR 0016's separate, still-unlocked question of which verticals the Playbook runs, or committing to any second tool.

`NmapBridge` exposes exactly two methods, `tcp_connect_scan` and `service_version_scan`, both declared `required_extent="recon"` and `mutates=False, consequential=False`: standard network recon, the canonical first category ADR 0012 itself names, not an exploitation primitive. Each method takes a `host` and an optional `ports` string, validated by regex before either ever reaches an argv list — a host starting with `-` or a ports string carrying anything but digits, commas, and hyphens is refused before `nmap` is ever invoked, the same defense-in-depth ADR 0018 already asks every bridge for. A value like `host="--script=vuln"` would otherwise let a proposed `tcp_connect_scan` smuggle in NSE script execution, a capability this bridge never declared and never intended to expose.

`exhaust run` wires `NmapBridge()` into its default bridge map, so a real run can now dispatch a `SandboxCall` or `RealTargetCall` naming `nmap` and get a real answer, not just an `UnknownToolError`. Proven against the real installed binary, not only a fake script a test substitutes for it: a live `tcp_connect_scan` against `127.0.0.1` returned nmap's real port-state output.

What this doesn't settle: which tool comes second, or whether nmap's own Nix-pinned version in the Rig's host environment (GLOSSARY.md's own description of the Rig) actually matches `7.992` — `PinnedTool.version` records the intended pin; nothing yet enforces that the binary `NmapBridge` finds on `PATH` is that exact version. That enforcement, and the Rig's actual provisioning mechanism, stay open questions this entry doesn't answer.

**Resolved**: the Rig's provisioning mechanism is now `flake.nix`, GLOSSARY.md's own stated starting point ("Exhaust provides it, starting with a Nix definition"), pinned to the exact nixpkgs commit NixHub indexes for nmap. That commit carries `7.991`, one patch behind the upstream tag this entry originally named, not `7.992` — nixpkgs hadn't caught up yet. Rather than leave that mismatch standing, `PINNED_TOOLS`' own `version` field was corrected to `7.991` to match what `nix develop` actually provisions, so the field means an enforceable pin again, not just a recorded intent. Verified, not assumed: `nix develop` was built and entered for real, `nmap --version` inside it printed `7.991`, and `NmapBridge` ran a real scan against it before `just check` (uv, lefthook, pytest, basedpyright, import-linter, the catalog check — all of it) was run from inside that same shell and passed clean. The remaining gap this still doesn't close: nothing enforces that an operator who skips Nix and relies on a system-installed `nmap` is running `7.991` specifically: that check, if ever added, is a separate `exhaust doctor`-style preflight, not this entry.
