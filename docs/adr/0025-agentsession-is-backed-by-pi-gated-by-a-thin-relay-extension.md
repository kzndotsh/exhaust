# `AgentSession`'s first implementation runs on Pi, gated by a thin extension that relays every decision to the Harness

`AgentSession`'s first concrete implementation drives Pi (`earendil-works/pi`, MIT-licensed), run as a subprocess over its own RPC wire protocol. The model loop, context and window management, retries, and compaction live inside Pi; everything that touches exhaust's own vocabulary stays exactly where it already lives. The Harness still does every `AgentAction` dispatch, the Scope Contract re-check on a `RealTargetCall`, the pending-approval logic, the Oracle, and the ledger, in Python, unchanged. Pi fills the one slot `AgentSession` was deliberately left open to hold: the actual conversation with a model, nothing more. No other exhaust module is aware Pi exists.

The gate is the part that makes this workable at all. Pi exposes a synchronous, blocking, fail-closed hook, fired before a proposed tool call executes and able to deny it with a reason. exhaust's own gate extension, loaded into the Pi subprocess, does not decide anything itself: it serializes the proposed call and forwards it, one connection per call, to the Harness process over a dedicated local channel this adapter owns outright, which maps it onto the matching `AgentAction` variant and runs it through the same dispatch, scope check, and ADR 0023 approval logic any other backend would, then sends the verdict back. That channel is deliberately not Pi's own RPC extension-UI subprotocol: that subprotocol's dialog methods auto-resolve with a default value if the client doesn't answer in time, and a hung decision silently defaulting to "allow" is exactly the failure this gate exists to rule out. The one piece of TypeScript this introduces has exactly one job, relay a decision, never make one; the decision itself is made entirely in Python, by code already covered by exhaust's own test suite.

Pi was chosen over a hand-rolled loop against a raw provider API, and over a single-vendor agent SDK, for three concrete reasons. It runs over fifteen-plus model providers through one abstraction, so the choice doesn't lock exhaust to one vendor the way an SDK shipped by that vendor would. Its gate is the most independently confirmed mechanism of anything evaluated: a dedicated research campaign found six unrelated third-party production systems, a line-by-line independent read of its own agent-loop source, a JetBrains-built IDE, a popular third-party desktop GUI, two unrelated community extensions, and a pure-Rust client with no Node or JavaScript runtime anywhere in its own code, all shipping that same before-the-call, can-block, fails-closed hook as their actual security boundary, not merely documenting it as a capability. And its licensing and distribution terms are unambiguous: a plain, unmodified MIT license verified directly from the repository's own file, no field-of-use restriction, no paid tier, no account requirement, no documented telemetry for the core project, a materially cleaner position than the genuinely unresolved subscription-usage policy question hanging over the alternative vendor SDK considered.

Three costs are accepted here knowingly, not discovered later. A credential proxy, per ADR 0021, is confirmed workable today for Anthropic and most API-key-based providers through one documented configuration field; Bedrock and Vertex authenticate through ambient cloud credentials instead, with no equivalent mechanism found, so those two providers are out of scope for this adapter until that's solved on its own. Pi does not load the gate extension into every session it spawns by default, so a background or scheduled subagent session created without explicitly requesting it runs ungated; every code path that creates a Pi session is therefore an obligation to load and verify the gate before it can propose any action, never an inherited guarantee. And Pi's own documentation warns that a hook which waits on the run's own completion can deadlock the session, a constraint the gate extension's implementation has to respect by construction, not find by testing. A fourth, lesser cost: two existing serious integrators of Pi are already carrying a real, acknowledged maintenance burden patching or mirroring around gaps in its current public SDK surface, a cost this adapter inherits too, ongoing rather than one-time.
