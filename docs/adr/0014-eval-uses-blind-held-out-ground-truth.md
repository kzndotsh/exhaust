# Exhaust's own effectiveness eval uses blind, held-out ground truth, scored independently

Whenever exhaust measures its own effectiveness, the fixtures it's scored against must be ones the Harness and its skills were never tuned on, the agent must never see the answer key during a run, and the score must come from a script re-deriving the result from raw evidence, never from the agent's own report of its result. Two concrete shapes satisfy this: a freshly generated secret or flag injected into the Sandbox per run and checked by exact string match after the run, or a withheld set of real-world cases (a patch-derived vulnerability, a real CVE) whose ground truth is never shown to the agent and whose fixture set is rotated so nothing gets tuned against it.

This is the one place in seven audited tools where a real, independently-recomputed score against true ground truth exists: a CVE-based held-out set, never exposed to the agent, scored by a script that re-derives the result from the agent's raw findings rather than trusting its self-report. We confirmed this by recomputing the score ourselves from the raw data and getting the same answer the project claims, exactly the bar an eval needs to clear.

Two failure modes to actively avoid, both found in the same project. First, scoring a system against the same list of expected answers it's being iteratively tuned against produces a rising score that looks like genuine improvement but is measurement of memorization, not of capability. Guard against this by holding a fraction of fixtures out of every tuning loop, and checking a score's trend against that held-out set specifically. Second, a good scoring mechanism accomplishes nothing if it isn't actually wired into every fixture it's meant to score: a clean flag-injection design with most of its own fixtures hardcoding a static answer that bypasses the injected one entirely makes the whole mechanism theater. Every fixture exhaust ships against this eval needs to be checked, not just designed, to confirm it actually exercises the real scoring path.

Two more lessons from a reverse-engineering toolkit audited separately. Its best-verified checks read raw bytes or actually execute a tool's output rather than trusting that tool's own report of what it did (an independent PCAP header parser that never calls the capture tool whose output it's checking; recovered source run for real and its actual program output compared against a known answer, not just its structure). An Oracle that trusts the very tool being checked to also report whether it checked correctly isn't independent at all; where exhaust's Oracle can replay evidence against the Sandbox and observe a real side effect, prefer that over inspecting the claim's shape. Separately, the same project's own test suite enforces, as an explicit rule, that a grader must never treat textual overlap with an expected answer as if it were factual correctness; a response that merely uses the right words is not the same as a response that is right, and conflating the two is an easy way for a benchmark to look like it's measuring capability while actually measuring vocabulary.

A fourth lesson, from a code-level teardown comparing five competing tools against identical CTF-flag benchmarks: a flag is an unambiguous oracle for one thing only, whether the single planted vulnerability was reached, and it is structurally blind to everything else that matters for real use. A target with one planted bug and one flag imposes no penalty for also reporting three findings that aren't real, so a high flag-solve rate says nothing about false-positive rate, and a curated single-path CTF says nothing about recall against the noise of a real, multi-vulnerability application. Exhaust's own eval needs a precision measurement alongside any recall measurement, not a bare solve rate, and at least one fixture shape with real noise (unplanted non-findings a correct run must not flag) rather than only a single clean target with one answer. The same teardown flags a sharper trap worth guarding against directly: when the flag-check lives in an external benchmark harness rather than in the tool's own shipped code, the score measures a capability the production tool doesn't actually carry into a real hunt. Exhaust's Oracle must be the same mechanism in both places, the one that runs during an actual Workspace investigation and the one that scores a benchmark, never a second, benchmark-only grader the shipped Harness doesn't have. Finally, a fixture drawn from a target that advertises its own known vulnerability (a named CVE in an unmodified container, for instance) risks measuring whether the agent recalls a public write-up rather than whether it can discover anything; prefer fixtures anonymized or novel enough that recall of a public PoC can't be mistaken for genuine capability. One of the benchmarks these five tools cite is itself a cautionary tale: its own maintainers now state, in the benchmark's own README, that it is saturated and the underlying vulnerabilities have been trained into current models, making a cited solve rate against it meaningless for any model or tool evaluated since. A held-out fixture set is not held out forever; it needs active rotation, not a one-time construction, against exactly this kind of after-the-fact contamination.

A fifth lesson, from an LLM vulnerability scanner widely used in an adjacent domain (probing a model's own output for unsafe content, rather than probing a live system for a vulnerability): reporting a bare point-estimate percentage from a fallible detector is itself a measurement error worth correcting for. That project's evaluator computes a non-parametric bootstrap confidence interval around its attack-success-rate metric, corrected using the detector's own known sensitivity and specificity, rather than reporting the raw hit count as if the detector were perfectly accurate. Exhaust's own eval reporting should hold to the same standard: any rate it reports (detection rate, false-positive rate, Verdict accuracy) should carry a confidence interval, and where the scoring detector or Oracle mechanism itself has a known error rate, that rate should correct the headline number rather than be reported alongside it as a disclaimer.
