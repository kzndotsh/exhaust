# A skill's description carries an explicit routing contract

Every skill's description states, in a fixed shape: what it does, naming real tools or techniques; an explicit "use when" trigger; and a negative trigger naming the nearest skill it could be confused with and when to reach for that one instead ("do not use for X, use `<other-skill>`"). This is enforced the same way for every skill in the Playbook, checked by a lint pass, not left to each skill's author's judgment.

A description is the only text an agent sees before deciding which skill to load; the body never gets read until that decision is already made. With a handful of verticals this barely matters, but once the Playbook's internal shape decomposes into many named sub-classes per vertical, as our research suggests it should (IDOR, BOLA, and BFLA as distinct items under access control, for instance, rather than one broad task), ambiguous routing between near-neighbor skills becomes a real, recurring failure mode. A library of 818 real-world cybersecurity skills, built by many different authors over time, enforces exactly this four-part description contract specifically to keep two skills from competing for the same request; it's the one convention in that project that held up at scale while its body-section template and its framework-ID mappings did not.
